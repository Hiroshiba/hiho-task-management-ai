# Asanaを唯一のタスク源流とする個人用AIタスク管理デスクトップアプリ

- 文書種別: 要件定義・基本設計
- 仮称: **TaskHub**
- 対象版: 初期版
- 作成日: 2026-08-26（JST）
- 対象OS: Windows / macOS
- 指定技術: Electron / Vite / TypeScript / Vue / Reka UI / Tailwind CSS / pnpm
- 前提利用者数: 1人
- 課金方針: Asana Personalの無料範囲を使用し、AIは既存のChatGPT/Codexサブスクリプションを使用する。OpenAI API課金は使用しない。
- テスト方針: 自動テスト・テストコードは実装対象外とする。末尾の受入条件は手動確認用であり、テスト実装の要求ではない。

---

## 1. 結論

本アプリは、次の構成とする。

1. **タスクの正本はAsana上の専用プロジェクトだけ**とする。
2. タスクの名称、説明、期限、進行状態、重要度、領域、親子関係は、無料のAsana公式UIでも最低限確認・編集できる形にする。
3. Asana Personalではカスタムフィールドとネイティブ依存関係を前提にできないため、無料で表示可能な情報は**セクション・タグ・期限・親子関係**で表現する。
4. 依存関係、Obsidianノートとの関連、停滞判定用の基準日など、Asana公式UIに表示する必要がない構造化情報は、Asana APIの**Custom external data**へ保存する。
5. Custom external dataはOAuthアプリごとに分離されるため、2台のPCでは**同じAsana OAuthアプリのClient ID**を使用する。
6. 実行順位はアプリ内で完全に決定論的に算出する。AIは重要度、期限、依存関係、領域などの候補を提案できるが、順位そのものを決めたり手動変更したりはできない。
7. CodexはOpenAI APIとして呼ばず、ユーザー環境にインストールされた**実際の `codex app-server` プロセス**をElectronのメインプロセスから起動する。
8. CodexにはAsanaの認証情報や書き込み手段を渡さない。Codexは構造化された変更案を返すだけとし、アプリが検証・表示し、ユーザー承認後にのみAsanaへ反映する。
9. Obsidianは登録済みVaultから読み取り専用で参照する。Discord等の外部情報源連携は初期版の対象外とする。
10. 未承認案はメモリに保持する。内部AIはターン専用のワークスペースで案を編集し、提出とターン成功後の検証を経て公開する。会話履歴やAI用コンテキストをGit管理しない。
11. ローカルには再構築可能なキャッシュ、承認済み操作の復旧ジャーナル、診断ログを置く。オフライン時はキャッシュ閲覧だけを許可し、変更をキューイングしない。
12. アプリからタスクを完全削除する操作は提供しない。「削除」に相当する操作はすべて**取り下げ**として表現する。

この構成であれば、Asanaを唯一のタスク源流に保ちながら、無料プランの制約、AI変更の承認、複数PC、Obsidian参照、決定論的な実行順位を同時に満たせる。

## 2. 調査から確定した外部制約

### 2.1 Asana Personal

Asana Personalは1〜2名向けの無料プランで、タスクとプロジェクトを利用できる。一方、公式料金表ではカスタムフィールドはStarter側の機能として扱われるため、本設計では無料プランで利用可能とは仮定しない。[R1]

Asana公式ヘルプは、カスタムフィールドを利用できないPersonalユーザーの分類手段としてタグを案内している。このため、重要度・領域・派生ブロック状態のAsana上での可視化にはタグを使用する。[R2]

Asanaのネイティブなタスク依存関係は有料プラン側の機能として案内されている。また、APIで有料機能を操作した場合はHTTP 402が返り得る。このため、無料範囲を保証する本アプリではネイティブ依存関係を使用しない。[R3][R4]

### 2.2 Custom external data

Asana APIのCustom external dataは、OAuthアプリ固有の構造化メタデータをタスクへ保存する仕組みである。内容はAsana公式UIには表示されず、別のOAuthアプリからも見えない。データ容量は1タスクあたり約32KBである。[R5]

この性質は、以下の要件と整合する。

- Asanaを正本にしたまま、無料プランにない構造化情報を保存できる。
- Obsidian関連情報をAsanaの説明欄へ混入させずに済む。
- AI用メモとユーザー向けメモを分離できる。
- ローカルDBを消しても、タスク固有メタデータをAsanaから再構築できる。

ただし、同じタスクでも別Client IDのOAuthアプリからはデータが見えない。そのため、2台のPCで同じアプリデータを見るには、同一のOAuthアプリ設定を使う必要がある。

### 2.3 認証

Custom external dataはOAuthが前提であるため、PATは採用しない。OAuthはPKCEを併用し、アクセストークンとリフレッシュトークンを使用する。リダイレクトURIは`urn:ietf:wg:oauth:2.0:oob`に固定する。[R6]

利用者はAsana Developer Consoleで個人用の非公開OAuthアプリを作成し、**Full permissions**を選ぶ。Redirect URLには`urn:ietf:wg:oauth:2.0:oob`を正確に登録する。TaskHubへClient IDとClient Secretを入力してブラウザで許可し、表示された認可コードを有効期限内にTaskHubへ貼り付ける。再認証も同じ方式で行う。認証待ち時間やローカルコールバックURLの入力は不要である。

Asanaの現行スコープ体系では、プロジェクト内セクションを含む本設計の全操作を細粒度スコープだけで安定して賄えない可能性がある。このため、初期版はユーザー自身が作成した非公開OAuthアプリを**Full permissions**で使用する。アプリ内部ではAPI操作を許可リスト方式に限定し、削除APIは実装しない。[R7]

これはトークン自体の権限が狭いことを意味しない。したがって、認証情報の保護とCodexからの隔離を必須要件とする。

### 2.4 Asana APIの同期制約

無料ドメインのAPIレート上限は毎分150リクエストである。並列数にも制限があり、429時には `Retry-After` に従う必要がある。[R8]

Events APIは同期トークンを利用した差分取得を提供する。初回または期限切れトークンでは412と新しい同期トークンが返るため、412をエラー扱いせず完全同期への切り替え契機とする。[R9]

Webhooksは外部から到達できる公開HTTPエンドポイントを必要とする。バックエンドを持たない個人用デスクトップアプリとは相性が悪いため採用しない。[R10]

ワークスペース横断のタスク検索APIは有料機能に依存するため、専用プロジェクト内のタスク一覧取得を同期の主経路にする。[R11]

### 2.5 Codex

Codex app-serverは、認証、スレッド、承認、ストリーミングイベントを扱うリッチクライアント向けインターフェースである。標準入出力上のJSONLプロトコルで起動でき、スレッド開始時に作業ディレクトリ、サンドボックス、承認方針などを指定できる。[R12]

CodexはChatGPTアカウントでログインでき、APIキーを使用する経路とは別にサブスクリプション利用経路がある。本アプリはChatGPTログイン経路だけを正式対応とする。[R13]

Codexは作業開始時に `AGENTS.md` とスキルを読み込む。本アプリではTaskHub専用ワークスペースのものだけを対象とし、通常のCodexホームにある設定、MCP定義、プラグイン、ホーム側スキル、セッションを継承しない。[R14]

Codex版文字列による事前拒否は行わず、検出したCodexを実際に起動して必要な能力とプラットフォーム別のサンドボックスを確認する。必要な確認ができない場合はAI機能だけを停止する。[R15]

### 2.6 Electron

Electron公式のセキュリティ指針に従い、RendererからNode.jsを直接利用させず、context isolation、sandbox、CSP、狭いpreload API、IPC入力検証を必須とする。[R16]

AsanaのOAuth Client Secret、アクセストークン、リフレッシュトークンはRendererとCodexへ渡さず、ElectronメインプロセスだけがOSの保護機構を介して扱う。Electronの `safeStorage` はOS提供の暗号化機構を利用できる。[R17]

## 3. 目的

### 3.1 主目的

利用者が、現在存在する全タスクについて次を低い管理コストで把握できるようにする。

- どの順番で着手すべきか。
- 何がいつまでか。
- 何が重要か。
- 何が未着手・進行中・完了・取り下げか。
- 何が他のタスクに完全または部分的にブロックされているか。
- タスクに関連するObsidianノートは何か。
- タスク追加・整理・状況照会を自然言語で行う場合、AIがどの変更を提案しようとしているか。

### 3.2 補助目的

- Asana公式UIからも、最低限の状態、期限、重要度、領域を確認・編集できるようにする。
- 2台のPCから利用しても、Asana同期後に同じタスク状態と同じ実行順位へ収束させる。
- AIの誤推測による作成、変更、完了、取り下げを、承認境界で防止する。
- AIが登録済みのObsidian Vaultを必要時に調べられるようにしつつ、Vaultへ書き込ませない。
- TaskHub専用ホームとワークスペースで認証・セッション・`AGENTS.md`・スキルを分離し、障害調査を容易にする。

## 4. 非目標

初期版では次を対象外とする。

- Asana以外のタスク管理サービスとの双方向同期。
- アプリ独自クラウド、サーバー、Web版、モバイル版。
- AI会話履歴、未承認変更案、ローカルキャッシュの端末間同期。
- アプリ終了前のCodexセッションを検索・再開する機能。
- AIによる常時バックグラウンド監視・自動変更。
- Obsidian、Discord、その他外部情報源への書き込み。
- Discord Bot、Discordログ、その他の外部情報源との読み取り連携。
- ストーリーポイントの保存または順位計算への利用。
- 実行順位の手動並べ替え。
- 保留状態。
- タスクの完全削除。
- Asanaの繰り返し設定の作成・編集・系列管理。
- Asana公式UIだけで全機能を操作可能にすること。
- 自動テスト、テストコード、テスト用モック基盤。
- 実装工程、工数見積り、リリース日程の策定。

## 5. 用語

| 用語 | 意味 |
|---|---|
| 正本 | タスクの最終的な事実を保持する場所。本設計ではAsana。 |
| 専用プロジェクト | アプリが管理する全タスクを所属させる、1つのAsanaプロジェクト。 |
| GUI変更 | 利用者がアプリのフォーム・ボタンを直接操作して行う変更。基本情報と関係情報は値の変更確定時に自動保存する。 |
| AI変更 | Codexの推論結果を原因として生成された変更。必ず承認後に反映する。 |
| 整合化 | Asana上の不完全・矛盾した表現を、決定済みの規則で正規形へ直す処理。AI推論ではない。 |
| 実行順位 | 現在着手可能なタスクを、決定論的な式で一意に並べた順位。 |
| 重要度 | タスク自体の価値・影響度を表す1〜5の利用者入力値。実行順位とは異なる。 |
| 完全ブロック | 現時点で、そのタスクについて意味のある独立作業が存在しない状態。 |
| 一部ブロック | 一部は待ち状態だが、独立して進められる作業が残る状態。 |
| 変更案 | AIが返す、まだAsanaへ適用されていない構造化操作群。 |
| 外部メタデータ | Asana Custom external dataに保存する、公式UIには表示しないタスク情報。 |
| 外部情報源 | Obsidian等、タスクの判断材料として読み取るが正本にはしない情報源。初期版ではObsidianだけを扱う。 |

## 6. システム不変条件

以下は常に成立させる。

1. アプリが管理するタスクは、必ず専用Asanaプロジェクトへ直接所属する。
2. タスクの正本はAsanaであり、ローカルDBだけに存在するタスクを作らない。
3. AIはAsana認証情報を持たず、Asanaへ直接書き込めない。
4. AI由来の変更は、利用者が承認するまでAsanaへ送信しない。
5. GUIによる直接変更は、オンライン時、基本情報と関係情報の値を確定した時にAsanaへ送信する。
6. オフライン時は、Asanaへ反映すべき操作を新規作成・保留しない。
7. アプリはAsanaのタスク削除APIを呼ばない。
8. 重要度は必ず1〜5のいずれかである。
9. 実行順位は一意であり、同じAsana状態・同じ基準時刻・同じアプリ版なら全端末で一致する。
10. 実行順位に所要時間を使用しない。
11. 進行中であること自体を実行順位の加点に使用しない。
12. 完全ブロックのタスクは、通常一覧では既定で表示しない。
13. 一部ブロックのタスクは、通常一覧へ表示する。
14. AIは新しい領域を提案しない。既存領域または未分類だけを選ぶ。
15. AIは明示的な根拠なしに完了・取り下げを提案しない。
16. 1つの成果を複数タスクへ分割する提案は、利用者が分割を明示的に依頼した場合に限る。
17. Obsidian Vaultは読み取り専用である。
18. 未承認変更案は再起動後へ持ち越さない。内部AIの編集用ワークスペースはメモリに保持し、ターン終了後に破棄する。
19. Codexスレッドはアプリ起動ごとに新規作成する。
20. アプリ終了前のスレッドを復元する機能は設けない。
21. 同期済み状態から導出する一覧、詳細、フィルター、件数、順位などの表示は、同じ同期済み事実に基づく。書き込み結果が未確認の状態を同期成功として扱わない。

## 7. Asana上のデータモデル

### 7.1 専用プロジェクト

初回設定で、利用者は次のどちらかを選ぶ。

- アプリに専用プロジェクトを新規作成させる。
- 既存プロジェクトを専用プロジェクトとして指定する。

既存プロジェクトを選んだ場合も、アプリ管理外のワークフローと混在させないことを前提とする。タスクが他プロジェクトにも所属すること自体は禁止しないが、状態は専用プロジェクト内のセクションで決める。Asanaの完了フラグはタスク全体に作用するため、同じタスクを別プロジェクトの異なる状態管理へ流用することは非推奨とする。

プロジェクトGIDと各セクションGIDは端末ローカル設定に保存する。タスク情報ではないため、これをローカルに持ってもAsana正本の原則には反しない。新しい端末では、同名セクションを検出して設定を再構築する。

### 7.2 セクションと進行状態

セクションは次の4つだけを状態表現として使用する。

| 順序 | セクション名 | 内部状態 | Asana `completed` |
|---:|---|---|---|
| 1 | `01 未着手` | `not_started` | `false` |
| 2 | `02 進行中` | `in_progress` | `false` |
| 3 | `90 完了` | `completed` | `true` |
| 4 | `99 取り下げ` | `withdrawn` | `true` |

保留状態は設けない。

セクションはGIDで識別する。名前が変更された場合、既に設定済みの端末では状態判定を継続できるが、整合性警告を表示する。セクションが削除された場合は、該当する書き込みを停止し、修復操作を要求する。

追加セクションの作成は妨げないが、追加セクションは状態として解釈しない。追加セクションへ置かれた管理対象タスクは「状態不明」として要整理一覧へ出し、利用者のGUI操作または明示的な整合化で4状態のいずれかへ戻す。

### 7.3 Asana完了フラグとの整合化

Asana公式UIでは、チェックボックス操作とセクション移動が独立して起きる。このため、直前スナップショットとの差分で意図を判定する。

1. セクションだけが変化した場合は、セクション変更を優先し、`completed` を対応値へ合わせる。
2. `completed` だけが変化した場合は、チェック操作を優先する。
   - `false → true`: `90 完了` へ移動する。
   - `true → false`: 外部メタデータの `last_active_status` に対応するアクティブセクションへ戻す。値がなければ `01 未着手` とする。
3. セクションと `completed` が同時に変化した場合は、4つの正規セクションへの明示移動を優先する。
4. 初回読込で履歴がない場合は、次の順で判定する。
   - `99 取り下げ` にあるなら取り下げ。
   - `90 完了` にある、または `completed=true` なら完了。
   - `02 進行中` にあるなら進行中。
   - それ以外は未着手。

整合化は決定論的なデータ修復でありAI変更ではないため、個別承認を要求しない。ただし、何を修復したかは通知領域へ表示する。

### 7.4 タグ名前空間

仮称のアプリ名前空間を `TaskHub/` とする。製品名決定時に固定し、以後変更しない。

#### 重要度タグ

- `TaskHub/重要度/1`
- `TaskHub/重要度/2`
- `TaskHub/重要度/3`
- `TaskHub/重要度/4`
- `TaskHub/重要度/5`

各タスクは正確に1つを持つ。

#### 領域タグ

- `TaskHub/領域/未分類`
- `TaskHub/領域/<既存領域名>`

各タスクは正確に1つを持つ。領域一覧は、同じワークスペースに存在する `TaskHub/領域/` プレフィックスのタグから構成する。

新しい領域を作れるのは、利用者がアプリ設定またはAsana公式UIで明示操作した場合だけとする。AIは既存領域からの選択または未分類のみを提案できる。

#### ブロック状態タグ

- `TaskHub/ブロック/なし`
- `TaskHub/ブロック/一部`
- `TaskHub/ブロック/完全`

各タスクは正確に1つを持つ。ただし、このタグは依存情報から算出した表示用キャッシュであり、直接編集の入力値にはしない。Asanaから手動で変更されても、次回同期時に算出値へ戻す。

#### その他のタグ

アプリ名前空間外のタグは保持し、一切削除しない。

### 7.5 タグ競合の扱い

#### 重要度

- 重要度タグがない: 重要度3を付与する。
- 複数ある: 一時的な順位計算では最も高い値を採用し、要整理として表示する。自動削除はせず、利用者がGUIで1つ選ぶか、AI提案を承認した時点で正規化する。

高い方を一時採用するのは、競合中に重要なタスクを不当に下げないためである。

#### 領域

- 領域タグがない: 未分類を付与する。
- 複数ある: 順位計算上は未分類として扱い、要整理へ出す。勝手に1つへ決めない。

#### ブロック状態

依存グラフから常に再計算し、競合タグを除去して正確に1つへ正規化する。

### 7.6 期限

Asanaの `due_on` または `due_at` を使用する。期限なしを正式に認める。

- `due_at` がある場合は、その時刻をJSTへ変換して評価する。
- `due_on` だけの場合は、その日のJST 23:59:59を順位計算上の期限とする。
- 期限と目標日は分けない。

画面では、一覧と詳細で同じ期限判定と色分けを使用する。未完了タスクは `due_at` が現在時刻より前、または `due_on` がJSTの本日より前なら期限超過として赤系で表示する。本日が期限の未超過タスクは黄系で表示し、未来または期限なしは通常色または控えめな色で表示する。完了と取り下げのタスクは期限超過の文字を残しつつ警告色を抑える。期限日時が同日中に超過した場合も「本日」と表示せず、期限超過と明示する。色だけで状態を判断させず、期限の具体的な日付または日時と状態文字を併記する。

### 7.7 所要時間

所要時間はタスクごとに任意で保存する。値は安全な整数と単位の組で、単位は `minute`、`hour`、`day`、`week`、`month` のいずれかとする。分は15以上、その他の単位は1以上とし、単位間の換算や刻みは設けない。

所要時間は対象タスクを実行する作業量を表し、期限までの残り期間や相手の返答待ちなどの待機期間は含めない。

新規タスクはAIが粗い単一単位で所要時間を見積もる。既存タスクの未設定値は必要に応じて提案し、設定済み値は明示的な変更または再推定依頼がある場合だけ変更する。所要時間は順位計算や活動基準日に使用しない。

### 7.8 親子関係

Asanaのネイティブな親・サブタスク関係を使用する。サブタスクはAsana上で自動的にプロジェクト所属にならない場合があるため、アプリは専用プロジェクト配下の親からサブタスクを再帰取得し、見つかったサブタスクを専用プロジェクトへ直接追加する。[R18]

これにより、「アプリが扱う全タスクが専用プロジェクトへ必ず所属する」という不変条件を守る。

親子関係の追加・変更は次の扱いとする。

- GUIで値を確定: 変更確定時に反映。
- AIが既存タスク同士の親子関係を推測: 変更案として提示し、承認後に反映。
- 新しい子タスクを作る分割: 利用者が分割を明示依頼した場合だけ提案可能。
- 明示的に列挙された複数の独立タスクをそのまま登録することは、「1タスクの分割」とはみなさない。

### 7.9 Asanaから直接作成されたタスク

専用プロジェクトで直接作られたタスクは、次回同期で自動採用する。

既定値は次の通りとする。

- 状態: セクションと完了フラグから判定。判定不能なら未着手。
- 重要度: 3。
- 領域: 未分類。
- ブロック状態: なし。
- 期限: Asana上の値をそのまま使用。
- 所要時間: Custom external dataにあれば使用し、なければ未設定とする。
- AI解析: 自動実行しない。利用者がそのタスクを開く、編集する、またはAIへ問い合わせた時点で候補解析を実行できる。

既定タグ付与と外部メタデータ初期化は、AI推論を含まない整合化として自動実行できる。

### 7.10 取り下げ

アプリ内に「完全削除」は存在しない。

- GUIの削除相当操作は「取り下げ」と表示する。
- AIへの「消して」「削除して」という依頼も取り下げとして扱う。
- 取り下げ時は `99 取り下げ` へ移動し、`completed=true` とする。
- AsanaのDELETE API、プロジェクトからの除外APIを、削除目的では呼ばない。
- 取り下げタスクは通常一覧から除外し、フィルターで表示できる。
- 取り下げから復帰する場合は、未着手または進行中を利用者が選ぶ。

Asana公式UIから利用者自身が完全削除することは技術的に防止できない。同期時に消失を検出した場合は、自動再作成せず「Asana上で削除された可能性」として要整理へ出す。復元はAsanaのごみ箱等から利用者が行う。

### 7.11 繰り返しタスク

繰り返し設定そのものは読み書き・編集・系列管理しない。

Asana側の繰り返し機能によって新しい発生タスクが専用プロジェクトに現れた場合は、通常の直接作成タスクとして採用する。元タスクとの系列性を順位や依存処理に利用しない。

## 8. Custom external data

### 8.1 保存目的

次だけを保存する。

- アプリ内部の安定識別子。
- 外部メタデータのスキーマ版。
- 最後のアクティブ状態。
- 停滞ペナルティ用の活動基準日。
- 親タスク自身に独立作業があるか。
- タスクの所要時間見積。
- 無料プランで表現できない依存関係。
- Obsidianノートへの相対リンク。
- 書き込み診断情報。

次は保存しない。

- AI会話全文。
- Codexのスレッド内容。
- AI専用の長文メモ。
- 対象外の外部情報源から取得した本文。
- Asanaの名称・説明・期限の複製。
- 実行順位や点数。
- 未承認変更案。

### 8.2 スキーマ

```json
{
  "schema": 1,
  "id": "8d6d40f1-0e8e-4f20-8b7f-2eefb3f613da",
  "rev": 12,
  "last_active_status": "not_started",
  "activity_anchor_on": "2026-08-26",
  "duration": {
    "value": 2,
    "unit": "hour"
  },
  "parent_work_mode": "unknown",
  "dependencies": [
    {
      "task_gid": "1234567890",
      "scope": "full",
      "source": "user"
    }
  ],
  "obsidian_links": [
    {
      "vault_id": "main",
      "path": "projects/example.md",
      "title": "Example",
      "confidence": 0.93
    }
  ],
  "provenance": {
    "created_via": "asana",
    "last_writer": "device-uuid"
  }
}
```

### 8.3 フィールド定義

| フィールド | 意味 |
|---|---|
| `schema` | スキーマ版。未知の新しい版は上書きせず読み取り専用にする。 |
| `id` | アプリ固有UUID。再送・重複作成検知に使用する。 |
| `rev` | 診断用の単調増加番号。AsanaにCASがないため、排他保証には使用しない。 |
| `last_active_status` | 完了解除時に戻す未着手・進行中の状態。 |
| `activity_anchor_on` | 停滞ペナルティの基準日。 |
| `duration` | 所要時間の見積。値は安全な整数、単位は `minute` / `hour` / `day` / `week` / `month`。未設定でもよい。 |
| `parent_work_mode` | `unknown` / `children_only` / `has_own_work`。 |
| `dependencies` | このタスクが依存する他タスクと、完全・部分の別。 |
| `obsidian_links` | Vault ID、相対パス、タイトル、AI判断時の信頼度。 |
| `provenance` | 作成経路と最終書込端末。診断専用。 |

### 8.4 容量上限

約32KBの上限へ余裕を持たせるため、初期版では次の制限を置く。

- 依存関係: 1タスク64件まで。
- Obsidianリンク: 1タスク10件まで。
- パスとタイトルはUTF-8換算で各1,024バイトまで。
- 保存前JSONは24KBを推奨上限、28KBを強制上限とする。
- 上限超過時は既存データを切り捨てず、変更を拒否して要整理へ出す。

### 8.5 `external.gid`

`external.gid` は次の形式とする。

```text
TaskHub:v1:task:<UUID>
```

AI変更案で新規タスクを作る場合、承認前にUUIDを発行し、作成要求へ使用する。API応答喪失後は§13.8に従って復旧し、作成結果のGIDが不明な場合は専用プロジェクト内タスクを走査して同じ `external.gid` を探す。

### 8.6 OAuthアプリ同一性

Custom external dataはOAuthアプリ単位で分離される。このため、2台目のPCでは1台目と同じClient IDを設定する。

2台目で別Client IDを使った場合、既存タスクの外部メタデータが空に見える。アプリは以下の兆候を検知したら、新規初期化で上書きせず警告する。

- 専用タグとセクションが存在する。
- 管理対象タスクが10件以上ある。
- しかし、全タスクのCustom external dataが取得できない。

警告文は「同一のAsana OAuthアプリ設定が必要」とし、認証設定をやり直すまで外部メタデータ書き込みを停止する。

## 9. 依存関係とブロック状態

### 9.1 依存関係モデル

無料プランではAsanaネイティブ依存関係を使用しない。依存関係は、依存する側のタスクのCustom external dataに保存する。

```text
Task A --depends on(full)--> Task B
```

これは「Task Aを進めるにはTask Bの完了が必要」を意味する。

各辺は次のどちらかである。

- `full`: Task Bが未完了ならTask Aには意味のある独立作業がない。
- `partial`: Task Bが未完了でもTask Aに独立して進められる作業が残る。

依存先の完了判定は `completed` 状態ではなく、本アプリの正規状態で行う。

- 完了: 依存を満たす。
- 未着手・進行中: 依存を満たさない。
- 取り下げ: 依存を満たしたとはみなさない。依存経路が失われたため要整理。
- 消失・アクセス不能: 満たしたとはみなさず要整理。

### 9.2 明示的ブロック状態

各タスクのブロック状態は、依存辺と親子関係から決定論的に算出し、UIとAsanaタグへ明示する。

1. 未完了の `full` 依存が1件以上ある: **完全ブロック**。
2. `full` はないが、未完了の `partial` 依存が1件以上ある: **一部ブロック**。
3. 未完了依存がない: **ブロックなし**。
4. 循環依存に含まれる: **完全ブロック**として通常一覧から除外し、循環エラーを表示する。

### 9.3 親タスクと子タスク

親タスクには `parent_work_mode` を持たせる。

| 値 | 意味 |
|---|---|
| `children_only` | 親自体には独立作業がなく、子の集合を表すだけ。 |
| `has_own_work` | 子タスク以外に親自身の作業が残り得る。 |
| `unknown` | 判断材料が足りない。 |

未完了子タスクが存在する場合の扱いは次の通りとする。

- `children_only`: 親は完全ブロック相当とし、通常一覧から隠す。
- `has_own_work`: 親は一部ブロックとして順位対象に残す。
- `unknown`: 独立作業を見落とさないため、一部ブロックとして順位対象に残す。

全子タスクが完了した場合:

- `children_only`: 通常順位から除外し、「完了確認」一覧へ出す。
- `has_own_work`: 親を通常順位へ残す。
- `unknown`: 親を通常順位へ残す。

`children_only` が利用者の明示操作または承認済みAI提案で設定され、全子タスクが完了している場合は、親完了を提案するための構造的根拠として扱える。ただし、自動完了はしない。

### 9.4 循環依存

依存グラフに強連結成分が存在し、2タスク以上の循環または自己依存がある場合、該当タスクを次のように扱う。

- 通常順位から除外。
- ブロック状態を完全とする。
- 「依存関係の循環」として要整理へ出す。
- AI変更案の検証時に、新しい循環を作る案を拒否する。
- 既存循環の自動削除は行わない。GUI操作または承認済み案で解消する。

### 9.5 表示規則

通常一覧の既定条件は次の通りとする。

- 未着手または進行中。
- 完全ブロックではない。
- 循環エラーではない。
- `children_only` かつ全子完了の完了確認待ちではない。

一部ブロックは表示し、ブロック理由と順位減点を示す。

フィルターで次を個別表示できる。

- 完全ブロック。
- 完了。
- 取り下げ。
- 完了確認。
- 整合性エラー。

## 10. 決定論的な実行順位

### 10.1 原則

実行順位はAI出力ではなく、アプリ内の固定式で算出する。

AIが提案できるのは、式の入力となる以下の値だけである。

- 重要度。
- 期限。
- 領域。
- 依存関係。
- 親子関係と親自身の作業有無。
- 状態。

これらもAI由来なら承認が必要である。

### 10.2 順位対象

次をすべて満たすタスクだけを順位対象とする。

- 状態が未着手または進行中。
- 完全ブロックではない。
- 循環依存ではない。
- `children_only` の完了確認待ちではない。
- 正規化不能な重大エラー状態ではない。

### 10.3 点数式

```text
実行点 = 重要度点
       + 期限点
       + 解放点
       - 一部ブロック減点
       - 停滞減点
```

#### 重要度点

| 重要度 | 点 |
|---:|---:|
| 1 | 0 |
| 2 | 25 |
| 3 | 50 |
| 4 | 75 |
| 5 | 100 |

重要度は順位の主軸だが、絶対優先ではない。期限超過や他タスクの解放効果によって、低い重要度のタスクが上へ来る余地を残す。

#### 期限点

基準時刻はJSTとする。

| 期限まで | 点 |
|---|---:|
| 期限なし | 0 |
| 31日以上 | 2 |
| 15〜30日 | 7 |
| 8〜14日 | 14 |
| 4〜7日 | 22 |
| 2〜3日 | 30 |
| 翌日 | 38 |
| 当日 | 46 |
| 1〜2日超過 | 54 |
| 3〜7日超過 | 62 |
| 8日以上超過 | 68 |

期限が近いだけで必ず最上位にはならない。たとえば、重要度1で8日超過したタスクは68点であり、期限なしの重要度4は75点なので後者が上になる。一方、重要度3で1日超過したタスクは104点となり、期限なしの重要度5を上回る。

#### 解放点

当該タスクの完了により、他タスクのブロックが軽減される効果を加点する。

| 直接影響する未完了タスク数 | 基本点 |
|---:|---:|
| 0 | 0 |
| 1 | 4 |
| 2 | 7 |
| 3以上 | 10 |

さらに、影響先に期限超過または7日以内のタスクが1件以上あれば2点を加える。解放点の上限は12点とする。

親子関係については、`children_only` の親を完了へ近づける子タスクも影響先として数える。

#### 一部ブロック減点

一部ブロック中のタスクは16点減点する。

完全ブロックは点数を付けず、順位対象外とする。

#### 停滞減点

長期間残っているだけのタスクが固定的に上位を占有しないよう、`activity_anchor_on` からの経過日数を使う。

- 60日までは0点。
- 61日以降、完了した30日ごとに2点減点。
- 最大12点減点。

式:

```text
停滞減点 = min(12, max(0, floor((経過日数 - 60) / 30) + 1) * 2)
```

`activity_anchor_on` は、次の実質的変更が起きた日に更新する。

- タイトルまたは説明の変更。
- 期限、重要度、領域の変更。
- 依存関係、親子関係、`parent_work_mode` の変更。
- 完了・取り下げからアクティブ状態への復帰。
- 利用者がGUIで「今日の作業を記録」を実行した場合。

次では更新しない。

- ブロックタグの再計算。
- タグ競合の機械的正規化。
- Asana上の表示順変更。
- 同期時刻更新。
- Codexが単にタスクを読んだこと。

Asanaから初めて採用したタスクは、作成日を基準日とする。

### 10.4 一意な並び順

実行点が同じ場合、次の順で比較する。

1. 実行点の降順。
2. 実効期限の昇順。期限なしは最後。
3. 重要度の降順。
4. 解放点の降順。
5. `activity_anchor_on` の降順。
6. AsanaタスクGIDの辞書順昇順。

最後にGIDを使うため、必ず一意になる。

順位は1から連番で表示し、次の契機で再計算する。

- 同期完了。
- GUI変更の反映完了。
- AI変更案の適用完了。
- JSTの日付変更。
- 利用者による手動再計算。

### 10.5 順位理由

順位の短い要約は常時表示し、点数内訳と全理由は初期状態で閉じた「順位の計算根拠」に集約して表示する。

例:

```text
重要度4 +75
期限5日 +22
2件を解放 +7
一部ブロック -16
停滞4か月 -4
```

「順位の計算根拠」には、全入力値、点数内訳、除外理由、タイブレーク結果を表示する。

AIが順位理由の自然言語説明を生成する必要はない。アプリが固定テンプレートで説明することで、同じ状態に対して常に同じ説明を返す。

### 10.6 Asana上の並び

デスクトップアプリ内のグローバル順位を正本とする。Asana公式UIでは、`01 未着手` と `02 進行中` の各セクション内をグローバル順位順へ近づける。

Asana APIのプロジェクト所属更新による挿入位置指定を用い、必要な移動だけを遅延実行する。[R19]

- アクティブセクション内だけを並べ替える。
- 完了・取り下げは順位同期しない。
- 連続した変更は数秒まとめる。
- APIレート余裕が少ない場合は並べ替えを後回しにする。
- Asanaから利用者が手動並べ替えしても、次回同期後に決定論的順位へ戻す。

## 11. AI機能の責務

### 11.1 AIができること

- 利用者の発言から新規タスク候補を抽出する。
- タスクのタイトル・説明・期限・所要時間・重要度・領域・状態変更を提案する。
- 新規タスクの作成案には必ず所要時間を含め、粗い単一単位で見積もる。既存タスクの所要時間が未設定なら必要に応じて推定案を提示し、設定済み値は明示的な変更または再推定依頼がある場合だけ変更する。
- 既存タスク同士の依存関係または親子関係を提案する。
- 明示的な分割依頼がある場合に限り、親タスクと子タスクの作成を提案する。
- Obsidianから関連ノートを検索し、関連付けを提案する。
- 登録済みObsidian Vaultの最新メモや本文を読み、ノートについての質問に答える。
- 現在のタスク状態、期限、順位理由、ブロック理由を説明する。
- 明示的根拠がある場合に限り、完了または取り下げを提案する。
- 不足情報が重大な場合だけ質問する。

### 11.2 AIができないこと

- Asana APIを直接呼ぶ。
- Asana認証情報を読む。
- ユーザー承認なしでタスクを変更する。
- 実行点または順位を直接設定する。
- 重要度を1〜5以外へ設定する。
- 新しい領域を作る、または作成提案する。
- タスクを完全削除する。
- Obsidianへ書き込む。
- 不活動、期限超過、更新の少なさだけを根拠に完了・取り下げを提案する。
- 明示依頼なしに1成果を多数の将来タスクへ分割する。
- アプリ起動だけを契機に全タスクを自動解析する。

### 11.3 質問と推測の方針

AIは質問を最小限にする。

自然言語の意図、事実報告、対象、値の関係は、操作ごとの意味条件をTaskHub専用ワークスペースの `AGENTS.md` の固定指示へ置き、AIに判断させる。アプリは語句の一覧、文末、完全一致で意図を判定せず、出典、操作、対象、基準値、権限、競合状態を固定ロジックで検証する。

新規タスクについて情報が足りない場合の既定値:

- 重要度: 3。
- 期限: なし。
- 所要時間: タイトルと要求内容から粗い単一単位で推定する。
- 領域: 未分類。
- 状態: 未着手。
- ブロック: なし。
- 親: なし。

次の場合は質問を優先する。

- 何をタスクとして登録するか自体が曖昧。
- 日付表現が複数解釈でき、期限を誤る可能性が高い。
- 「最優先」「絶対必要」等の表現と既定重要度3が明らかに矛盾する。
- 完了・取り下げの対象タスクを一意に特定できない。
- 複数既存領域が同程度に該当し、未分類では利用者の意図を大きく損ねる。

質問せず推測した項目は、変更案で「推測」と明示する。

### 11.4 分割判定

AIは、利用者が1つの成果を複数の実行可能な子作業へ分解するよう明示的に依頼した意味を抽出できた場合だけ、分割として扱う。親タスクを一意に特定でき、各子作業の指示がその親タスクへ結び付いていることも必要とする。

次は分割とはみなさない。

- 利用者が複数の独立タスクを列挙した。
- 既存の複数タスクを親の下へ整理するよう求めた。
- 1件のタスクを登録し、説明欄にチェック事項を書いた。

### 11.5 完了・取り下げの根拠

AIが完了または取り下げを提案できる根拠は次に限定する。

1. 利用可能な利用者原文で対象を一意に特定でき、その対象の作業が完了した事実を本人の報告として述べている。対象と意味が明白なら、追加の確認を求めず完了案を提示できる。
2. 利用者が対象タスクを取り下げる意思を明示している。削除を求める意味も取り下げの意思として扱うが、完了の事実報告とは区別する。
3. 対象タスク自身の基準スナップショットにある `notes` に、対象を一意に特定できる完了または中止の明示記述がある。
4. `parent_work_mode=children_only` が利用者によって明示または承認済みで、全子タスクが完了している。

外部Codexから受け取った利用者原文は、§12.8の出典照合とGUIでの確認を経て、その操作の根拠として扱う。

引用、否定、伝聞、仮定、条件、対象の取り違え、対象の一部だけの完了は、利用者本人による対象全体の完了報告や取り下げ意思とはみなさない。利用者が対象や意思を訂正した場合は、後の明確な発言を優先する。訂正後も対象または操作を一意に決められない場合は質問する。

対象が曖昧な取り下げ依頼では、アプリが候補1件のタスク名、GID、取り下げ操作を示して確認する。その確認への次の返答が明示的な肯定なら、対象GIDと取り下げ操作に固定した利用者の発言を根拠として扱う。別タスクへの返答、否定、保留、複数候補や複数質問への曖昧な肯定は根拠としない。確認回答のsourceは、同じAIワークフローサービスのインスタンス内で、元の対象GIDと `status`、`completed` が当該ターンの基準スナップショットと一致する場合だけ、同じ対象への `withdraw` に再利用できる。

次は根拠として認めない。

- 長期間更新されていない。
- 期限を過ぎている。
- 関連情報が見つからない。
- AIが「おそらく終わっている」と推測した。
- 別タスクが完了しただけで、対象タスクの完了を直接示していない。

変更案には、根拠の種類と参照位置を必須で含める。

## 12. Codex統合

### 12.1 起動方式

Electronメインプロセスが、ユーザー環境から検出したCodex CLIを直接起動する。Codex版文字列だけで起動前に拒否せず、起動後の能力確認で利用可否を決める。

```text
codex app-server
```

要件:

- `shell: false` で実行する。
- macOSでは、GUI起動時にもHomebrew版Codexを検出できるよう、既存のPATHを優先しながら`/opt/homebrew/bin`と`/usr/local/bin`を探索先へ追加する。
- Windows以外ではPATHで検出したCodexのシンボリックリンクを実体パスへ解決し、実体パスで起動する。
- 標準入力・標準出力をJSONLプロトコルに使用する。
- 接続時にAppsとPluginsを明示的に無効化する。
- 標準エラーの本文と接続処理の元の例外を診断ログへ渡す。文字列置換で判別できる秘密値は伏せ字にし、エラーメッセージとスタックトレースを保存する。
- OpenAI API SDKやAPIキー経路へ置き換えない。
- Codexプロセスが見つからない、または必要な能力とプラットフォーム別のサンドボックスを確認できない場合、AI機能だけを無効化する。Asanaの閲覧・GUI編集は継続可能とする。

### 12.2 認証

Codex標準のChatGPTアカウント認証を使用する。

- `CODEX_HOME` に `<TaskHub userData>/codex-home/` を指定して、TaskHub専用ホームを作成する。
- 通常のCodexホームから認証ファイルをコピーせず、通常のCodexホーム、設定、MCP定義、プラグイン、ホーム側スキル、セッションを参照・継承しない。
- 初回設定でTaskHub専用ホームからChatGPTログインを一度行い、そのホームの認証状態を以後の接続に使用する。
- 未ログインなら、app-serverのChatGPTログイン開始機能を使ってブラウザまたはデバイスコード認証へ誘導する。
- APIキーによる経路は正式対応しない。
- 認証ファイルとOSキーチェーンの場所や形式をアプリが独自に複製しない。

認証とTaskHubで作成したセッションはTaskHub専用ホームへ保存する。通常のCodexホームとは分離する。

### 12.3 スレッドと会話履歴

- アプリ起動時に `thread/start` で新しいCodexスレッドを必ず作る。
- 依頼ごとに独立した接続、作業ディレクトリ、Codexスレッドを作り、複数の依頼を並行実行できる。
- アプリ起動中の依頼は一覧から選び直し、会話、質問への回答、変更案の承認を続けられる。
- Rendererは各依頼と応答を組で保持し、古い順に上から下へ表示する。応答の本文と質問は次の送信後も確認でき、入力欄は会話と変更案などの操作の下に置く。
- TaskHub専用ホームに保存されたセッション履歴をアプリが一覧・復帰する機能は実装しない。
- 通常のCodexホームに保存されたセッション履歴は読み込まない。
- アプリ独自の会話DB、Git同期、端末間同期は作らない。
- Rendererに表示中の会話は、アプリ終了時に失われてもよい。

依頼ごとに会話、対象タスク、実行状態、未承認案を分離する。新しい依頼を開始しても、他の依頼の状態は変更しない。IPC要求とストリーミング通知はセッション識別子で対応付ける。

ダイアログを閉じても依頼は継続する。明示的な中止では、その依頼の実行を停止して接続と未承認案を破棄する。完了結果を確認して依頼を片付けた場合も接続を解放する。アプリ終了時はすべての依頼を停止し、再起動後には復元しない。

利用者原文のsource mapは、AIワークフローサービス `AiWorkflowService` の同じインスタンス内でメモリに保持する。正常に完了したターンの利用者原文と確認回答は、`base_proposal_id` の有無にかかわらず、過去のsource IDを指定して参照できる。この原文の再利用では、AIが現在の要求に即して意味を判断する。成功した原文の保持には `completedEvidenceSources`、各変更案に結び付いた出典の保持には `StoredProposal.source_map` を使い、別の履歴保存先は作らない。失敗または中断したターンの未確定な原文は、成功したターンの根拠として保持しない。再試行を含む1つの論理ターンにはsource IDを1つだけ発行し、成功しなければその論理ターンの未確定分だけ破棄する。サービスのインスタンスを終了するときにsource mapをすべて破棄し、アプリの再起動後へ持ち越さない。設定変更や保留確認のリセットだけではsource mapを破棄しない。

AIの推論は並行実行し、変更案の適用はアプリ全体で1件ずつ行う。承認時の現在状態の取得、基準値との競合検査、適用後の読み戻し検証を行う。

タスク参照と外部ツールの接続先、外部ツールから取得した根拠も依頼ごとに分離する。認証には共通のTaskHub専用ホームを使い、認証ファイルは複製しない。依頼を終了すると、その依頼の接続と作業ディレクトリを解放する。Codexスレッドの過去文だけを自然言語根拠として信頼せず、利用者原文の根拠参照はアプリが保持するsource mapから解決する。

新規セッションの開始に認証が必要な場合は開始成功として扱わず、入力欄へフォーカスしない。

### 12.4 作業ディレクトリ

アプリ専用のCodex作業ディレクトリを、OSごとのユーザーデータ領域に作る。

例:

```text
<TaskHub userData>/codex-workspace/
```

内容:

- `AGENTS.md`: アプリ固有の厳格な役割・禁止事項・変更案形式。
- `.agents/skills/`: Asana状態照会とObsidian参照の利用方法。
- `bin/`: 読み取り専用コマンドの薄いクライアント。
- `tmp/`: 当該起動中だけ使用する一時領域。

含めないもの:

- Asanaトークン。
- Asana Client Secret。
- タスク全件の永続スナップショット。
- 会話要約・長期メモ。
- Obsidian本文の複製。

`tmp/` は起動時に初期化する。作業ディレクトリはGit管理しない。

内部AIの変更案は、§13のメモリ上の編集用ワークスペースで管理する。Codex作業ディレクトリには変更案や検証エラーのファイルを作成しない。

app-serverから返る `instructionSources` を確認し、TaskHub専用ワークスペースの `AGENTS.md` が読み込まれていない場合はAI機能を開始しない。通常のCodexホーム側の指示やスキルは読み込まない。

### 12.5 サンドボックス

Codexターンは次の権限で開始する。

- 承認方針: `never`。ローカル読み取りコマンドごとの確認は出さない。
- ネットワーク: Codexのシェルからは無効。
- Asanaの資格情報と書き込み手段: Codexへ渡さない。

Windows以外ではTaskHub専用権限プロファイルを使用する。書き込みは専用作業ディレクトリの一時領域だけに許可し、専用作業ディレクトリと登録済みObsidian Vaultを読み取れるようにする。Codexの起動に使う実体ファイルだけを読み取り許可へ追加し、親ディレクトリ全体は許可しない。Obsidian Vaultは読み取り専用とし、モデルが実行するシェルコマンドから `CODEX_HOME` を読み取れないようにする。

WindowsではCodex標準の `workspace-write` を要求する。非昇格WindowsサンドボックスはTaskHubが必要とする分割読取制限を強制できないため、TaskHub専用権限プロファイルを使用しない。実効サンドボックスはネットワーク無効の `workspaceWrite` または、より制限の強い `readOnly` だけを許可する。`dangerFullAccess` と `externalSandbox` は許可しない。`workspaceWrite` が適用された場合は専用作業ディレクトリ全体が書き込み可能になる。どちらの場合も、モデル側コマンドから専用 `CODEX_HOME` や登録済みVaultを読み取れないことは保証しない。Asana資格情報の非共有は維持する。この制約はWindows版を実用可能にする残余リスクとして受け入れる。[R23]

Codex app-server自体は全OSで認証のため専用 `CODEX_HOME` へアクセスできる。検出したCodexでプラットフォーム別のサンドボックスを構成できない場合は、AI機能を無効化する。

### 12.6 起動時の能力確認

起動時に次を検査する。

1. `CODEX_HOME` がTaskHub専用ホームを指し、通常のCodexホームを継承していない。
2. 検出したCodexを起動でき、`codex --version` の結果を取得できる。版文字列で事前拒否しない。
3. app-serverの `initialize` / `initialized` が成功する。
4. モデル一覧またはモデル情報を取得できる。
5. `thread/start` がTaskHub専用ワークスペース、プラットフォーム別の制限付きサンドボックスを受理し、Web検索を無効として開始できる。Windows以外ではTaskHub専用権限プロファイルも確認する。
6. Structured Outputs互換の外側スキーマを指定し、返された `response_json` を既存のTaskHub応答スキーマで検証できる。[R24]
7. `instructionSources` からTaskHub専用ワークスペースの `AGENTS.md` を確認できる。
8. TaskHub専用ワークスペースのスキル一覧取得またはスキル読込が利用できる。
9. ChatGPTアカウントで認証済みであることを確認できる。
10. AppsとPluginsの無効設定を指定して接続が成功する。

必要な能力またはプラットフォーム別のサンドボックスを確認できない場合は、AI機能だけを停止する。Asanaの閲覧とGUI編集は継続可能とする。

通常設定に由来するMCPの二段階探索、実行時のMCP名変換、実験的機能の全件監査、未知の機能に対する肯定的な許可リストは行わない。検出したCodex版ごとの未公開機能を完全に監査しないことは残余リスクとして受け入れる。

### 12.7 taskctl読み取りツール

CodexへAsana APIやシェル実行権限を渡す代わりに、同期済みローカルキャッシュを読むdynamic tool `taskctl` を提供する。Codexは許可されたcommandと必要な引数だけを渡し、メインプロセス内の読み取り専用ローカルブローカーが処理する。AIの標準経路ではshellやCLIからtaskctlを実行しない。

例:

```json
{"command":"rank"}
{"command":"get","gid":"<task-gid>"}
{"command":"search-local","query":"<text>"}
```

性質:

- 読み取り専用。
- Asana認証情報を持たない。
- 最新同期時刻を必ず出力する。
- 応答は既定のZodスキーマで検証したJSONとする。
- タスク変更コマンドを一切提供しない。
- 取得件数、出力サイズ、実行時間に上限を設ける。
- app-serverからのdynamic tool要求は、`taskctl`、§14の `obsidian`、§13の `proposal_workspace` だけを受理する。

AIターン開始前にオンライン同期を行う。同期に失敗した場合は、古い情報であることを明示した質問応答だけを許可するか、変更案生成を停止する。初期版では安全側に倒し、同期失敗時は変更案生成を停止する。

macOSのtaskctl Unixソケットは、ユーザーデータパスやTMPDIRの長さに依存しないよう、`/private/tmp` 配下へ起動ごとの0700専用ディレクトリを作成して配置する。接続情報ファイルは専用ワークスペースの `tmp/taskctl-connection.json` に残し、ソケットの実パスだけをTaskHub権限プロファイルの `network.unix_sockets` へ許可する。

### 12.8 外部Codexからの利用

通常のCodex CLIから `$taskhub` を明示して、起動中のTaskHubのタスクを参照し、変更案を編集・提出できるようにする。外部連携プロトコルは3とする。タスクの読み取りと提案できる操作はTaskHub内部のAIと揃え、読み取り契約、§13の提案形式、`ProposalWorkspace`、検証器、承認・適用処理を共有する。対象はWindows上のTaskHubと同じPCのWSL、macOS上のTaskHubと同じMacのターミナルである。TaskHub内部のAIセッションやCodexへのログインは不要だが、タスク参照と変更案にはAsanaの初回設定と同期が必要になる。

入口は明示呼び出し専用Skill、アプリ同梱CLI、ローカルIPC、本体の共通処理を順につなぐ。起動中のアプリをCLIから操作するObsidianと、WSLからWindows側のElectronを起動するVS Codeを先例とする。[R30][R31] MCPを常設せず、日常の呼び出しで接続設定を切り替えない。Skillの `agents/openai.yaml` に `policy.allow_implicit_invocation: false` を指定する。この設定は暗黙のSkill選択を抑止するものであり、シェルからの直接実行を禁止する認可機構ではない。取得済みのタスク情報は会話に残り得る。[R25]

CLIの入口は `agent-info` と `request` に固定し、後者の入力は標準入力のJSONとする。`operation` に操作名を指定し、利用者の文章をシェルの実行文字列へ埋め込まない。標準出力はJSONとし、操作結果を `output` に返す。診断は標準エラーへ出し、`ok=false` または `output.kind=error` の失敗は非ゼロの終了コードで示す。提出結果の成否は `output.result.kind` で確認する。

| 操作 | 役割 |
|---|---|
| `agent-info` | 稼働中本体の版、プロトコル、起動インスタンス、接続先の文脈、時刻、同期状態、利用可能な操作と入力形式を返す。 |
| `tasks.list` | `taskctl` の `list` と同じ条件と応答でタスク一覧を返す。 |
| `tasks.get` | `taskctl` の `get` と同じ条件と応答でタスクの詳細を返す。 |
| `tasks.rank` | `taskctl` の `rank` と同じ条件と応答で実行順位を返す。 |
| `tasks.graph` | `taskctl` の `graph` と同じ条件と応答でタスクの関係を返す。 |
| `tasks.areas` | `taskctl` の `areas` と同じ条件と応答で領域を返す。 |
| `tasks.search-local` | `taskctl` の `search-local` と同じ条件と応答でローカルのタスクを検索する。 |
| `proposals.prepare` | 利用者原文と基準スナップショットを固定し、提案コンテキストと空のワークスペースを作る。 |
| `proposals.read` | 現在の改訂番号を指定し、ワークスペースの概要、変更案全体、グループ、操作を読む。 |
| `proposals.apply-edits` | IDで指定したグループや操作などの編集を、バッチ単位で原子的に適用する。 |
| `proposals.diff` | 指定した改訂番号から現在までの意味差分を読む。 |
| `proposals.validate` | 提出条件と操作ごとの基本・グラフ検証結果を、案を変更せずに返す。 |
| `proposals.submit` | 完成案と全操作の根拠を検証し、封印して承認待ちの案を登録する。 |
| `proposals.status` | 変更案の現在状態と、提案に含まれる各操作の適用結果を返す。 |
| `review.open` | 指定の変更案をTaskHubの確認画面で開く。 |

変更案を作る前に `proposals.prepare` へ `request_id`、`agent-info` の `instance_id`、接続先の `context_id` と `project_gid`、利用者原文の `source_text` を渡す。本体は `BaselineSnapshot` と読み取り用の `TaskctlSnapshot` を固定し、ランダムな `proposal_context_id` と `workspace_id`、初期値0の `revision`、`turn_context`、`evidence_locator_prefix` を返す。6種類のタスク読み取りは任意の `proposal_context_id` を受け取り、指定時は固定したスナップショット、未指定時は現在の同期済みキャッシュを読む。変更案の生成には固定した情報を使う。

ワークスペースの読み取り、編集、差分、検証、提出には、準備時の `instance_id`、`context_id`、`project_gid` と、返された `proposal_context_id`、`workspace_id` を必須とする。読み取りと差分には現在の `revision`、編集・検証・提出には現在の `expected_revision` を指定し、異なる基準やワークスペースの組合せを拒否する。差分には `from_revision` も指定する。古い改訂番号には `code=stale_revision` と `current_revision` を返し、その番号で現在の案を読み直して追加編集を組み立て直す。編集中の基準ハッシュと変更前値には準備時の値を使い、編集や提出で基準スナップショットを取り直さない。

`proposals.apply-edits` は、`edit_batch_id` と `edits` 配列で§13.1の意味編集を受け付ける。初回は `replace_all` に完全な `Proposal` を渡して構築でき、大きな案はタイトル、グループ、操作を分けて追加できる。追加編集では `group_id` と `operation_id` を保持する。バッチ全体が成功したときだけ `revision` を1増やし、編集応答に完成状態と不備の件数を返す。途中の未完成状態は保持できる。§13.2の全17操作と複数グループを扱い、編集バッチの上限は128 KiBとする。期限はそのタスク自身の確定した期限だけを指定するようSkillに記載し、関連する予定や不確かな日付は説明に残す。

ワークスペースの読み取り・編集・差分・検証・提出応答は、外側の通信形式の領域を残して63 KiB以下とする。`proposals.read` は概要、案全体、グループ、操作を選べ、読み取りと差分の `content` は分割したJSON文字列として返す。続きの取得は、同じ改訂番号と対象を保ち、返された `next_offset` を次の `offset` に指定する。全ページの文字列を順に連結してJSONを復元する。検証結果は `review.offset` から最大50項目で、同じ `expected_revision` を保ち、`review.next_offset` を次の要求の `offset` に指定する。

外部から届く原文は `external_review`、その明示根拠は `external_review_explicit` として扱い、内部AIの `user_message` として信頼しない。全操作の `evidence_refs` に、準備時の原文にそのまま含まれる空でない `excerpt` と、`external-review:<proposal_context_id>:<operation_id>` 形式のlocatorを持つ外部根拠を必須とする。完了・取り下げの `status_evidence.reference` と、分割の `creation.instruction_reference` も、その操作の外部根拠と一致させる。GUIには原文、対象、操作を表示し、承認時には選択した操作の根拠を再検証する。汎用locatorや外部Codex自身の文章だけを明示根拠に昇格させない。

`proposals.validate` は、完成形のスキーマ、基準ハッシュ、全操作の原文根拠を提出条件として検証する。不備があれば `can_submit=false` と `review.kind=issues` を返し、`issue_count` と `issues` に件数と不備を示す。提出条件を満たせば `can_submit=true` と `review.kind=operations` を返す。この `entries` は `kind=operation` の操作判定と `kind=diagnostic` の診断を含み、`entry_count` は両者の合計、`operation_count` は操作数とする。操作判定には `basic.kind`、`graph.kind`、`eligible`、診断には `phase=basic` または `phase=graph` とコード、メッセージを示す。項目ごとにページングし、全ページの `group_id` と `operation_id` で判定と診断を対応付ける。不備と診断の長文メッセージは省略して `message_truncated=true` を付ける。基本・グラフ検証が不適合の操作もGUIの部分採用レビューへ残すため、提出可能であることと、全操作が適用可能であることを区別する。

提出前に `proposals.read` の概要から、グループ順・各グループ内の操作順に全 `operation_ids` を保持する。`proposals.submit` は、準備とは別の新しい `request_id` で指定した改訂番号の案を検証し、提出に成功するとワークスペースを封印する。応答は `result.kind=submitted`、`proposal_id`、`request_id`、`operation_count`、現在の `state_kind` を返す。不備があれば `result.kind=invalid` を返し、同じワークスペースで検証と編集を続けられる。訂正した改訂番号の提出には新しい `request_id` を使う。

外部CLIには承認操作を設けない。新規提出は承認待ちとし、`review.open` へ提案IDを渡して確認画面を開く。変更案は内部AIと共通の `AiWorkflowProposalView` と承認UIを使い、適用可能なグループまたは非一括の操作を選択できる。提出後の案はGUIで編集、却下、承認する。提出時とGUI編集後に既存の提案検証器で検証し、GUIで編集した値は§13.6の明示選択として扱う。承認後に既存の適用処理で選択した変更をAsanaへ反映する。外部Codexは受理直後に「承認待ち」と報告し、操作ごとの適用結果を確認するまで反映済みと報告しない。

読み取りには同期時刻と同期状態を添える。同期済みキャッシュがなければ利用不可とし、オフラインでキャッシュがあれば閲覧だけを許可する。同期には整合修復の書き込みも含まれるため、外部の読み取りで同期を暗黙に開始しない。オフライン中の変更案をオンライン復帰待ちの変更キューとして受け付けない。

WindowsではWSLのBashからWindows版Electronを `ELECTRON_RUN_AS_NODE=1` で直接起動し、Windows内で名前付きパイプへ接続する。EXEのパスだけを `wslpath -u` で変換し、クライアントスクリプトはWindows形式のパスで渡す。既存の `WSLENV` を保持して環境変数を伝播する。この経路はWSLとWindows間のTCP接続を必要としないが、Windows実行ファイルとの相互運用が有効でなければならない。[R27][R28]

macOSではアプリ内のElectronを同じ環境変数で直接起動し、短い専用ディレクトリのUnixドメインソケットへ接続する。`wslpath` と `WSLENV` は使わない。どちらもNode.jsの別インストールを要求しない。Electronの `runAsNode` fuseを有効に保ち、配布版の標準入出力と終了コードを検証する。[R29]

外部連携は初期状態で無効とし、GUIでの有効化を保存する。管理先は `app.getPath('userData')/external-agent` とする。`skill/` の下へSkill本文、メタデータ、Bashランチャーを配置し、クライアント本体と秘密の接続情報はその外へ置く。初回登録は利用するWSLまたはMacのターミナルで行い、`~/.agents/skills/taskhub` から管理対象Skillへのシンボリックリンクを作る。別の同名Skillを上書きしない。

Codexのサンドボックスでランチャーの実行が制限される場合は、利用者が明示して専用コマンドだけの実行ルールを登録する。Skill自身は権限設定を変更しない。`bash` 全般や任意のシェル文字列を許可せず、固定したランチャーの引数列に限定する。Rulesは起動時に読み込まれるため登録後はCodexを再起動する。管理者の制限が優先される環境ではユーザーのルールだけで許可できるとは限らない。[R26]

アプリの主プロセスが起動時に管理対象のSkillとCLIを更新し、現在の実行ファイルへの参照を書き直す。管理先が同じなら本体更新や実行ファイルの移動に追従する。別のアプリデータへ移動した場合は登録を修復する。本体停止時は接続不能を返し、別のTaskHubの探索や自動起動はしない。

資源を一時ファイルから置き換えて待受を開始し、最後に接続情報を公開する。複数ファイルの置換だけで版の一致を保証せず、接続時にプロトコルと起動インスタンスを照合する。不一致時は実行を拒否し、古い形式へのフォールバックをしない。Skillは呼び出すたびに `agent-info` で本体の操作仕様を取得する。Skillの即時再読み込みや、既に会話へ読み込まれた説明の更新には依存しない。本体自身の自動ダウンロードとインストールはこの連携機能の対象外である。[R25]

認可には起動ごとに発行するランダムなcapabilityを使う。接続情報はユーザーデータ配下へ配置し、既存のパス検証と原子的置換を使う。Unixでは所有者と0700のディレクトリ、0600のファイルを検証し、Windowsでは親ディレクトリから継承するアクセス権を使う。独自のWindows ACL設定・検証は行わない。Windowsのパイプへ接続できることだけでは認可しない。秘密値をSkill本文、公開する接続案内、応答、ログへ含めない。入力サイズ、接続数、応答サイズ、待ち時間に上限を設ける。

準備と提出では `request_id` と元の入力内容を照合する。同じIDと内容の再送には、同じ提案コンテキスト、提出の不備、または同じ提案IDと現在状態を返す。編集は同じ `edit_batch_id` と入力内容の再送に初回の編集結果を返し、再適用しない。異なる内容でのID再利用は拒否する。提出の再送でGUI編集後の内容を元に戻さない。非同期の基準値取得より先に準備の受付を予約し、応答喪失や同時再送で基準や提案を二重に作らない。受理後の処理はソケット切断に連動して取り消さない。

固定したスナップショット、利用者原文、ワークスペース、未承認案と要求IDの対応はメモリだけで保持する。却下や適用後もアプリ終了までは提出の受付キーを保持し、上限に達したら新規受付を拒否する。GUIの提案の版はワークスペースの改訂番号とは独立に管理する。選択変更、編集、承認、却下のIPC要求には提案の版を必須とし、承認には適用範囲の選択も必須とする。古い画面からの操作と二重承認を拒否する。接続先変更、Asana再認証、連携の無効化、アプリ終了では固定した基準、ワークスペース、未承認案を失効させ、基準値取得中の要求も後から復活させない。基準値取得と適用は既存のアプリ全体のキューへ直列化し、承認準備、適用中状態、診断、競合、読み戻しを内部AIと共有する。

`proposals.status` は提案IDと提出前に保持した全 `operation_ids` を、提出した案と同じ順序で受け取る。メモリに提案がある間は `result.kind=current` とし、`result.proposal` に提案や文脈のID、改訂番号、出所、`operation_ids`、`state` を返す。`state.kind=finished` では `state.result.application.operations` から各操作の `outcome` を確認する。再起動後は既存の適用ジャーナルを照会して、操作ごとに `journal` または `unknown` を返す。部分承認された案を一つの成否へまとめず、要求IDだけから提案を復元しない。記録がない操作や適用結果が不明な操作を「未適用」と断定せず、自動で再提出しない。

## 13. AI変更案プロトコル

### 13.1 基本方針

TaskHub内部のCodexは、メインプロセスがメモリに保持する `ProposalWorkspace` をdynamic tool `proposal_workspace` で編集する。各Codexターンの開始前に同期済みの基準スナップショットを取得し、基準ハッシュへ結び付けた新しい `workspace_id` を発行する。訂正再試行でも、新しい基準とワークスペースを使用する。

ツールは実行中のスレッドID、ターンID、`workspace_id` を照合し、当該ターンのワークスペースだけを操作する。入力をZodで厳格に検証し、引数はUTF-8で128 KiB、各応答は64 KiBを上限とする。

| 操作 | 役割 |
|---|---|
| `read` | 現在の改訂番号を指定し、概要、変更案全体、グループ、操作を読む。 |
| `edit` | タイトルやグループの一括指定を変更し、グループと操作をIDで指定して追加・移動・削除、操作を置換する。`replace_all` による案全体の置換も提供する。 |
| `diff` | 指定した改訂番号から現在までの変更を、グループと操作のIDに基づく差分として読む。 |
| `validate` | 現在の案を変更せずに検証し、不備を返す。 |
| `submit` | 指定した改訂番号の完成案を検証し、提出済みとして封印する。 |

`revision` は0から始め、編集バッチの適用ごとに1増やす。各バッチは `edit_batch_id`、現在の `expected_revision`、編集操作の配列を持ち、全操作が成功した場合だけ反映する。同じバッチIDと同じ内容の再送は初回の結果を返し、再適用しない。同じバッチIDへの異なる内容、改訂番号の不一致、存在しない編集対象や重複IDは拒否する。グループや操作の移動では `group_id` と `operation_id` を保持し、操作の置換でも `operation_id` を変更しない。

編集中の `draft` では、タイトル未設定、空グループ、未解決の一時参照などを保持できる。IDの一意性と件数上限は編集時に検証し、完成案のスキーマや基準ハッシュとの不一致は不備として返す。上限は32グループ、1グループ64操作、案全体256操作とする。大きな案は編集を分割し、`read`、`diff`、`validate` は応答の `next_offset` を次の `offset` に指定して続きを取得する。`edit` は診断が大きくても適用結果と新しい `revision` を返し、不備の続きを `validate` で取得できる。

Codexの最終出力は、app-serverのStructured Outputs互換スキーマを使って構造化する。外側は必須の文字列 `response_json` だけを持つオブジェクトとし、その復号結果を `codexGeneratedResponseSchema` で厳格に検証する。全OSで、変更案がある場合は `kind=proposal`、提出済みの `workspace_id` と `revision`、短い説明と質問を返す。変更案がない場合は `no_proposal` と `pending_proposal_action` を返す。復号後の `response_json` はUTF-8で96 KiB以下とし、外側も200,000文字と256 KiBの上限内に収める。[R24]

`submit` の成功は案の封印だけを行う。新たな編集は受け付けず、承認UIへの公開やAsanaへの適用は行わない。Codexターンの成功後、最終応答と提出済みワークスペースのID・改訂番号を照合し、§13.5の検証を通った案だけを `StoredProposal` として保持して承認UIへ公開する。自由文 `message` は説明だけであり、適用対象は検証済みの `operations` とする。

提出済みワークスペースがあるターンで `no_proposal` を返した場合は不整合として訂正を求める。未提出のまま返した `no_proposal` は、`pending_proposal_action` に従って前案を保持または破棄する。

未承認案への追加依頼では、Rendererが表示中の `proposal_id` を `base_proposal_id` として明示し、backendが同じAIワークフローサービスのインスタンスに保持した検証済み案を新しいワークスペースの初期値にする。Codexは既存操作を読み、利用者が明示的に変更・撤回した操作を除いて引き継ぎ、複数項目の依頼は一つの変更案にまとめる。変更前値と基準ハッシュは当該ターンの基準スナップショットへ合わせ、根拠を現在のsource mapへ結び直す。各ターンのプロンプトには、基準コンテキスト、利用可能なsource一覧、引き継げる根拠対応、ワークスペースのID・改訂番号・基準ハッシュ、現在の要求を構造化して渡す。固定指示と動的データを分ける方針は、Prompt engineeringとReasoning best practicesに従う。[R32][R33]

前案の根拠対応を再利用できるのは、基本検証の不適合も含めた既存の操作グラフ検証で適用可能とされた操作に限る。承認UIの選択状態は承認する適用範囲を表し、未選択だけで操作の撤回とはみなさない。

`base_proposal_id` で指定した前案で出典と照合済みの `user_explicit` の状態根拠と分割依頼locatorを使う場合は、前案の操作と `StoredProposal.source_map` に保存した元source、空でない正確な `excerpt`、対象GIDと操作、分割の場合は親タスク参照の対応をすべて照合する。照合した対応を保ったまま、通常の根拠束縛処理で当該ターンのsource mapへ結び直す。locatorだけを許可一覧へ追加して根拠を信頼しない。対象、操作、親、引用を変える場合は、現在利用可能な原文のsourceとAIによる新たな意味判断を必要とする。

`notes` は当該ターンの対象タスク自身の `notes` のsource、外部状態は当該ターンのcollectorによる取得記録、`children_only` は当該ターンの親子構造と状態で再確認する。利用者が変更・撤回を明示していない前案の操作を再確認できない場合は、黙って除外せず、質問を伴う `no_proposal` と `pending_proposal_action=keep` を返す。

新案の保持と基準外部データの登録が成功してから、前案とその基準外部データ参照を解放する。生成失敗、`pending_proposal_action=keep`、新案の基準外部データの登録失敗では前案を保持する。全操作の明示的な撤回では `pending_proposal_action=discard` により前案を破棄し、前案がなければ状態を変更しない。却下時と承認結果が確定したときは既存の承認経路で案を破棄し、適用済みの案を引き継がない。指定された前案が同じサービスのインスタンスに存在しない場合はエラーとする。

Codexターンの終了時にワークスペースのツール操作を無効化し、試行の処理を終えるとワークスペースを破棄する。taskctlの固定スナップショットや根拠収集などのターン資源を解放してから、新案、前案の撤回、根拠原文などのターン結果を確定する。失敗や中断では編集中・提出済みの案を公開しない。

### 13.4 操作に必須の情報

各操作は次を持つ。

- `operation_id`。同じ変更案内では一意とし、別の変更案との重複は許可する。
- 対象タスクGID、または同じ変更案内の一時参照ID。
- 基準スナップショットのハッシュ。
- 変更前値。
- 変更後値。
- 理由。
- 推測か明示情報か。
- 信頼度。
- 根拠参照。利用者発言や `notes` の意味を根拠にする操作は、出典の `locator` と原文の `excerpt` を持つ。
- 分割に該当する場合は、利用者の明示依頼位置。
- 完了・取り下げの場合は、許可された根拠種別。

### 13.5 検証器

AIが自然言語の意味を判断し、アプリ側の固定ロジックが出典、ID、型、状態、権限、競合、承認条件を検証する。固定ロジックは、原文が実在すること、根拠が当該ターンのsource mapで解決できること、対象タスクと操作または分割の親へ結び付いていることを確認する。外部案の原文は§12.8の提案コンテキストから解決し、選択した操作へのGUI承認を根拠の確定条件とする。この確認は、AIが原文の意味を正しく解釈したことの証明ではない。

検証項目:

1. 操作種別が許可リストにある。
2. 対象タスクが専用プロジェクトの管理対象である。
3. 重要度が1〜5である。
4. 領域が現在存在する領域または未分類である。
5. 依存先が管理対象タスクである。
6. 依存グラフに循環を作らない。
7. 親子関係に循環を作らない。
8. 完了・取り下げの根拠種別が許可され、対応する出典または構造化状態を検証できる。
9. 利用者原文の根拠参照が当該ターンのsource mapに存在し、完了・取り下げの対象GIDと許可操作に一致する。
10. `notes` を根拠とする完了・取り下げでは、対象タスク自身の基準スナップショットの `notes` だけを参照している。
11. 分割の明示依頼参照が当該ターンのsource mapに存在し、各子操作の親タスク参照へ結び付いている。
12. 1成果から複数の新規子タスクを作る操作が、明示依頼の参照を持つ分割として宣言されている。
13. 変更前値が現在のAsana値と競合していない。
14. 外部メタデータ容量上限を超えない。
15. タスク削除・領域作成・順位上書き等の禁止項目を含まない。

自然言語を根拠にする操作では、空でない `excerpt` が出典の原文にそのまま含まれることを検証する。一般的な根拠locatorやGUI編集の汎用locatorを、この照合なしに完了・取り下げや分割の根拠へ昇格させない。AIの発言を利用者の原文として扱わない。

内部AIの `validate` と `submit` は、案全体のスキーマと基準ハッシュを検証し、構造が完成していれば根拠の束縛、基本検証、グラフ検証、全操作と全グループの適用可能性を確認する。`validate` の成功は提出を意味しない。`submit` が不備を返した場合も案は `draft` のままとし、Codexは返されたコードと位置を使って同じワークスペースを編集できる。

承認UIへの公開前には、Codexターンの成功、構造化応答、提出済みワークスペースのIDと改訂番号を確認する。封印した案を読み取り、根拠の束縛、基本検証、グラフ検証、全操作と全グループの適用可能性を再確認する。構造化応答、未提出、参照不一致、根拠、基本・グラフ検証、適用可能性の検証に失敗した案は表示せず、初回を含む最大3回の試行で訂正する。同じ内容が続いても1回の試行として数える。

再試行では、構造が完成した直近候補を、新しく取得した基準スナップショットへ結び直して新しいワークスペースへ引き継ぐ。直前の案が未完成なら、引き継げる直近候補または前案を初期値にする。検証エラーはメモリに保持し、試行回数と上限、型付きコード、JSON Pointer、特定できるグループIDと操作IDを次のプロンプトへ渡す。現在の候補の不備は当該ワークスペースの `validate` で確認する。

診断情報は§19.4に従い、試行回数と上限、候補と前回候補のハッシュ、同一内容かどうか、エラーのfingerprint、検証段階、型付きコード、JSON Pointer、特定できるグループIDと操作IDを記録する。候補ハッシュは、ワークスペースから取得した案のcanonical JSONのSHA-256とする。構造化応答自体の不正、未提出、参照不一致で候補を確定できない場合は、取得不能理由を `not_staged` とする。提案本文、根拠本文、会話、秘密情報は記録しない。

要求、同期、中断、外部情報の収集、外部書き込み、ターン資源の解放、診断ログ保存など、変更案の訂正で直らない失敗はAIによる訂正再試行の対象にしない。

### 13.6 承認UI

変更案はアプリ終了までメモリに保持する。

表示内容:

- 変更前と変更後。
- AIの理由。
- アプリが出典と照合した根拠の原文抜粋。
- 推測箇所。
- 影響するタスク数。
- 順位への予測影響。これはアプリの式で再計算する。
- 競合や検証警告。

操作:

- 案全体を承認。
- グループ単位で承認。
- 非一括の操作単位で適用範囲を選択。
- 値をGUIで修正して承認。
- 却下。
- AIへ質問して再提案させる。

利用者が値を編集した時点で、その最終値は利用者が明示選択したGUI変更として扱う。ただし、承認ボタンを押すまでAsanaへ送信しない。

GUI編集後は再検証する。適用不可になった操作は承認UI内で「適用不可」として表示し、選択対象から除外する。全体承認を無効化し、適用可能なグループまたは非一括操作だけを選択できるようにする。

### 13.7 適用手順

承認後は次の順で処理する。

1. 適用する操作全体の復旧計画を永続ジャーナルへ保存する。
2. 対象タスクをAsanaから再取得する。
3. 提案作成時の基準値と現在値を比較する。完了・取り下げの根拠が対象タスクの `notes` にある場合、その `notes` が基準スナップショットから変わっていれば適用しない。
4. 競合のない操作だけを確定する。
5. 新規タスクを、事前発行UUID付きで作成し、応答直後にGIDをジャーナルへ保存する。作成時の `data` には、検証済みの対象プロジェクトGIDを `projects` へ1件、同じプロジェクトGIDと目的セクションGIDの組を `memberships` へ1件指定する。`workspace` は送信しない。[R34]
6. 未適用のタイトル、説明、期限、タグ、状態を反映する。
7. 未適用の親子関係、依存関係、Obsidianリンクを反映する。
8. Asanaのタスク属性と外部メタデータを読み戻して検証する。
9. ローカルを再同期し、順位を再計算する。
10. 必要ならAsanaセクション内の表示順を遅延更新する。

新規タスクのタイトル、説明、期限、Custom external dataは作成時に指定する。外部作用が生じ得る作成送信は1操作につき1回に限り、401後の再送は§21.1に従う。GIDを保存してから後続処理へ進む。

作成POSTの拒否を外部作用なしと確定できるのは、`create_task` の作成POSTで、作成済みGIDがなく、最上位のエラーがRESTの直接 `AsanaHttpError` または既知の認証・支払い・レート制限エラーであり、原因連鎖のREST statusが一意で400、401、402、403、404、429、451のいずれかの場合だけである。任意の `AggregateError` 内にstatusがあるだけの場合、408、未知の4xx、5xx、応答なし、2xx本文の形式不正、作成後のGET・タグ・親操作の失敗は外部作用の可能性を残し、既存の復旧状態へ進める。401後の認証更新失敗は、最初のREST 401と更新失敗をcauseへ保持した認証エラーとして扱う。更新成功後の401は既存の一度だけの再送を維持する。

確定拒否では、元HTTPエラーのapplication journal診断をJSONLとSQLiteへ各1回ずつ厳格に試み、診断成否にかかわらず `journal.complete(not_applied)` を原子的に試みる。元HTTP診断が失敗してもcompletionが成功すればジャーナルは `not_applied` で確定し、未記録分を上位へ伝播する。completionに失敗した場合だけ別の診断を記録し、診断とcompletionの記録済み・未記録状態を合成して上位へ伝播する。元HTTP診断とcompletionがともに成功した場合だけ `not_applied` を返す。診断失敗やcompletion失敗で返す内容には内部reason codeを含めない。

作成直後は、`external`、`memberships` 内の対象プロジェクト、目的の `section` の未投影、またはGETの404だけを、上限を設けたGETで再観測する。この再観測では、作成要求や追加書き込みを再実行しない。目的外のセクション、作成時に指定したタスク属性やCustom external dataの不一致、別UUID、不正な `external` は直ちに競合として扱い、上書きしない。安全な初期状態を確認してから、未適用のタグと親タスクだけを設定する。

新規作成が失敗または未適用になった場合、その一時参照を対象タスク、親タスク、依存先に使う後続操作を同じ適用実行内で開始しない。これにより実行を阻止した新規作成の一時参照も利用不能とし、参照関係に沿って後続の作成要求や書き込みを阻止する。独立操作は継続し、利用不能な一時参照に依存する一括グループは全体を阻止する。

作成拒否の操作結果で `external_api_failed` を表示するときは、「Asanaへの反映に失敗し、変更は行われませんでした。詳細はエラーログを確認してください。」とし、内部reason codeを利用者向け文へ埋め込まない。`unknown` の要整理項目も、構造化reason codeは保持したまま、利用者向け文では事実と必要な行動へ写像する。

独立操作はAsana Batch APIを最大10件単位で利用できるが、バッチはトランザクションではない。[R20]

`atomic=true` は「開始前に全操作を検証し、可能なら一括して扱う」という論理指定であり、Asana側の原子的コミットを保証しない。途中失敗した場合、削除によるロールバックは行わず、適用済み・未適用を正確に表示し、修復案を作る。

### 13.8 適用中の永続ジャーナル

未承認案は永続化しない。利用者の承認後、外部APIを呼ぶ前に、適用する操作全体の復旧計画をローカルへ保存する。メモリ上の変更案が失われても、保存した計画だけで操作順、グループの一括指定、一時参照を復元できるようにする。

保存内容:

- `proposal_id`、`operation_id`、グループID、操作順、グループ順、`atomic`。
- 操作種別、対象GIDまたは一時参照、新規タスク用UUID、一時参照と作成済みGIDの対応。
- 承認時の変更前値と期待する変更後値、適用先プロジェクト・セクションなどの実行条件。
- Custom external dataの承認時点の基準値、または同じproposal内で基準値を生成する作成操作と一時参照。
- 開始時刻、適用段階、最終結果。

保存しない内容:

- 会話全文。
- 外部情報源の本文。
- Obsidian本文。
- Asana認証情報。

起動時に未完了ジャーナルがあれば、保存した計画と永続化済みの段階に従って復旧する。外部書き込みの直前に `write_started` を保存し、新規作成の応答直後にGIDと一時参照の対応を保存する。作成完了通知やUUIDの照合で判明したGIDは、後続の診断と適用結果にも保持し、保存失敗だけを理由に新規作成を再送しない。

新規作成が `prepared` の場合、同じUUIDのタスクが0件なら作成を開始できる。1件以上あればexternal IDの衝突として未適用にし、既存タスクを成功扱いしない。`write_started` で作成結果のGIDが不明な場合は、同じUUIDのタスクが1件だけなら内容を照合して再開する。0件または複数件なら結果を確定できないため再作成しない。

新規作成の復旧も、正常な保存済みの計画を使い、永続化済みの段階と観測済みの外部状態から未適用と確定できる処理だけを再開する。GIDや現在値の一致だけで成功や再開の可否を判定しない。`unknown` または未適用と確定した新規作成の一時参照は、GIDとの対応が保存されていても利用不能とする。復旧開始時と復旧中の結果確定時にこの制限を適用し、§13.7と同じ規則で後続操作を阻止する。対応表とジャーナルの履歴は保持する。適用済みの新規作成の一時参照や、利用不能な一時参照を使わない独立操作には、この制限を適用しない。

保存済みのGIDから新規作成を復旧する場合も、404と `external`、`memberships` 内の対象プロジェクト、目的の `section` の未投影だけを、§13.7と同じ上限を設けたGETで再観測する。目的外のセクションや値の不一致は直ちに競合とする。`final_result=unknown` と `read_back` 以降の段階では再観測しない。

Custom external dataの承認時の基準値は保存計画から取得する。同じproposal内で作成するタスクでは、保存した作成操作を基準値の出所とする。実行時や復旧時に読み取った現在値で承認時の基準値を置き換えない。

Asanaのタスク属性とCustom external dataは独立に、変更前、変更後、許可する部分適用、それ以外の第三状態へ分類する。変更後に一致する側へは書き込まず、不足側だけを再開する。状態更新で許可する部分適用は、目的のセクションへ移動済みで完了フラグが未更新の場合に限る。重要度・領域タグでは、変更先タグを追加済みで変更元タグが残る場合に限る。第三状態やマージ競合では書き込まない。

タスク属性とCustom external dataの両方を読み戻して検証してから `read_back`、`metadata_verified` へ進める。この2段階からの再適用・復旧では、操作の外部書き込みや読み戻しを再実行せず、ローカル同期と順位再計算だけを行う。`ranking_recalculated` では最終結果の保存だけを行う。ローカル同期に失敗した場合は `local_resync_required` とし、要整理を作らず、次回も保存済みの段階からローカル処理だけを再開する。

安全に再開できず未解決と確定した操作は、要整理や適用結果を公開する前に `final_result=unknown` を永続化する。`unknown` はどの適用段階からも復旧時に読み出すが、外部状態の再取得や書き込みの対象にはせず、一括グループと一時参照に依存する後続操作の実行阻止、要整理の再構築にだけ使う。復旧処理後は、復旧結果と残存ジャーナルの整合を検証し、要整理を置き換えてから復旧待ち状態を更新する。

`final_result=unknown`、復旧計画の破損・欠落、整合しない異常データは個別に手動で解消する。これらの実データ異常に合わせた移行、将来の互換処理、救済処理、フォールバックは追加しない。この方針は個別の実データ異常を対象とし、§16.1で定める既知の保存形式からの移行には適用しない。

## 14. Obsidian連携

### 14.1 基本方針

- 読み取り専用。
- Vaultはローカルディレクトリとして登録する。
- Git同期は本アプリの責務外。
- AI用メモをVaultへ生成しない。
- タスク情報をノートへ追記しない。
- Asana説明欄へノートタイトルを追記しない。
- 関連情報はCustom external dataだけに保存する。

AIは `obsidian` dynamic toolを通じて、main processの読み取りサービスから登録済みVaultの一覧、ノート一覧、検索結果、本文を取得する。Vault IDとMarkdownの相対パスを検証し、未登録VaultやVault外への参照は拒否する。CodexへVaultの絶対パスを渡す必要はなく、Windowsを含めてシェルの読み取り可否に依存しない。

最新メモはファイル更新日時の降順で取得し、同じ更新日時なら相対パスの昇順にする。取得件数は1〜100件で指定する。本文と取得結果は会話内で参照し、永続保存しない。タスクの完了・取り下げには、別途定める固定検証済みの根拠が必要である。

### 14.2 端末ごとのVault設定

各端末で次を設定する。

```text
vault_id: main
absolute_path: /Users/.../ObsidianVault
```

初回設定を終えた後も、ヘッダーの「設定」からVaultを追加し、登録済みVaultの絶対パスを変更できる。既存のVault IDは維持し、同じIDの参照先を更新する。

保存時はmain processでパスを検証し、実在するディレクトリの実体パスを端末のデータベースへ保存する。入力が無効な場合は保存せず、入力内容と以前の設定を保持する。保存した参照先は以後のノート参照とアプリの再起動後にも使用する。Windowsの起動時自動検出は未登録のVaultだけを登録し、設定済みの参照先を保持する。

AI依頼が古い参照先で処理を続けないよう、開始中または未終了のAI依頼がある場合は保存を受け付けない。利用者は各依頼の「確認して閉じる」または「依頼を中止」で依頼を閉じてから保存する。Codexの処理中や別の設定保存中も受け付けず、処理の完了を待つよう案内する。Codexが無効化されて処理が動いていない場合は、AI依頼や設定保存が残っていなければ保存できる。新しいAI依頼は保存済みの参照先を使用する。

Asanaには `vault_id` と相対パスだけを保存する。

これにより、WindowsとmacOSで絶対パスが違っても同じリンクを解決できる。2台目に対応Vaultがない場合は「この端末では利用不可」と表示し、関連付け自体は保持する。

### 14.3 AIによる自動関連付け

AI解析は、利用者が何かをしたタイミングだけで実行する。

対象契機:

- 新規タスクをAIへ依頼した。
- 既存タスクについてAIへ質問した。
- タスク詳細で「関連ノートを再解析」を押した。
- GUIでタスクを作成・大きく編集し、AI補助解析が有効である。

アプリ起動だけでは実行しない。

AIはファイル名、タイトル、見出し、Frontmatter、本文を読み、関連候補を出す。

- 明確な単一候補かつ信頼度0.85以上: 同じ変更案にリンク追加を含める。
- 複数候補が近い: 候補を示し、利用者に選択させる。
- 根拠が弱い: 関連付けない。

AI由来のリンク追加もタスク変更であるため、承認が必要である。

### 14.4 表示

タスク詳細には次を表示する。

- ノートタイトル。
- Vault名。
- 相対パス。
- ファイルの存在状態。
- 関連付け理由の短い説明。
- ローカルで開く操作。

ノート本文をAsanaへコピーしない。

### 14.5 ファイル変更

ノートが移動・改名された場合、リンク切れとして表示する。AIはユーザー操作を契機に再検索し、修正候補を変更案として出せる。自動で別ファイルへ付け替えない。

## 16. 同期と複数PC

### 16.1 正本とキャッシュ

Asanaを正本とし、タスクのローカルスナップショットは再構築可能なキャッシュとする。

ローカルに保持できるもの:

- タスクスナップショット。
- Custom external dataのスナップショット。
- タグ、セクション、親子関係。
- 算出済み順位と内訳。
- Events API同期トークン。
- 端末固有設定。
- Vaultパスマッピング。
- 最小限の適用ジャーナルと診断ログ。

ローカルだけに保持してはならないもの:

- タスク自体。
- 重要度・期限・状態・領域の唯一の値。
- 依存関係の唯一の値。
- Obsidian関連付けの唯一の値。

キャッシュを消しても、Asanaと端末設定から再構築できることを必須とする。

SQLiteの保存スキーマはv5とし、新規作成とv3・v4からv5への移行を扱う。v4の適用ジャーナルは、`recovery_reason` 列がない形とある形の既知の2種類だけを識別する。列がない場合の `legacy_unresolved` には `recovery_context_missing` を設定し、列がある場合は既存の理由を保持する。移行はトランザクション内で行い、未知の列構成や検査失敗ではロールバックする。データのコピー、テーブル構成と行数の検査、要整理項目の移行をすべて完了してからスキーマ版を更新する。

`operation_kind` がある現行形式のジャーナルは、完了済みや `unknown` でも復旧計画と対象参照を検証する。これらの最終結果が保存済みの行で破損を検出した場合は、legacyとして扱わず、元のcauseを保持した例外にする。legacyの完了行として受け入れるのは、`operation_kind` がない既知のv3完了行だけとする。

旧 `proposal_conflict` の要整理項目は、既知の固定文面に完全一致し、補完後の項目をZodで検証できる場合だけ `proposal_id` と `operation_id` を補う。未知の文面や補完条件を満たさない項目は変更せず保持する。

### 16.2 初回・完全同期

1. 専用プロジェクトのタスクをページング取得する。1ページ最大100件を前提とする。[R21]
2. 必要フィールドだけを `opt_fields` で指定する。
3. 各親タスクのサブタスクを再帰取得する。
4. プロジェクトへ直接所属していないサブタスクを検出する。
5. 必要な整合化を行う。
6. セクション・タグ・Custom external dataを取得する。
7. 依存グラフを構築する。
8. 順位を再計算する。
9. ローカルキャッシュを置き換える。

完全同期の主な契機:

- 初回起動。
- Events APIの412。
- 同期トークン破損。
- 整合性警告からの手動再構築。
- 24時間に1回の保険的同期。
- 利用者の「全データを再取得」。

### 16.3 差分同期

Events APIの同期トークンを端末ごとに保存する。

実行契機:

- アプリ起動後。
- ウィンドウがフォアグラウンドへ戻った時。
- オンライン中、約60秒間隔。
- AIターン開始前。
- GUI変更適用後。
- AI変更案適用後。

イベント本体をタスクの完全状態とはみなさず、影響したタスクを再取得する。`has_more` がある間はページを取り切る。

### 16.4 APIスケジューラ

全Asana API呼び出しを1つの中央スケジューラへ集約する。

- 読み取り並列数: 最大5。
- 書き込み並列数: 1。
- 毎分150件より十分低い内部予算を設定する。
- 429・5xxの再試行は§21.2に従い、再送安全な要求だけを対象にする。
- 表示順同期は低優先度。
- AIターン直前の鮮度確保を高優先度。

個々のAPI呼び出しとは別に、同期、GUI変更、AI変更案の適用、表示順同期をメインプロセスで操作単位に直列化する。読み取り、検証、書き込み、読み戻し、キャッシュ反映までを一つの操作として扱う。GUI変更とAI変更案の適用に伴う事後同期は、同じ操作の中で完了させる。

アプリによるAsana書き込み後の事後同期では、Events APIの差分通知だけを反映完了の根拠にしない。差分がない場合も書き込み対象を再取得して対象を含む同期済みスナップショットを確定し、そのスナップショットから一覧、詳細、フィルター、件数、順位などの派生状態を更新する。対象の確認と派生状態の更新が完了するまで、未確認の結果を同期成功として扱わない。

再認証による資格情報の切り替えも同じ実行順に従い、進行中の操作が終わってから行う。再認証前に受け付けた未実行の変更要求は失効させる。

定期同期と表示順同期の重複要求はまとめ、待機中の利用者操作を優先する。表示順同期の入力は実行順が来てから作る。AIターン開始前の同期と基準スナップショットの確定も保護するが、AIの回答生成中は他の操作を待たせない。

同期の事前確認は、共有するキューの実行処理内で行う。同期処理は `queued`、`preflighting`、`running` の段階と、背景処理または利用者要求を示すownerを持つ。`queued` の背景同期へ利用者要求が合流した場合は利用者優先キューへ積み直す。`preflighting` または `running` で合流した場合は処理を継続したままownerと結果の待機先を利用者要求へ移し、移管前の背景待機は中断結果で完了させる。失敗を診断するのは最終ownerだけとする。

### 16.5 GUI変更

オンライン時、基本情報と関係情報は値の変更確定時に保存要求を受け付ける。正常な同期済みデータがある場合は、同期中も保存要求を受け付け、実行順が来るまで待機する。初回同期前、同期失敗、オフライン、認証が必要な状態、復旧待ちでは受け付けない。

手順:

1. 対象タスクを編集基準ハッシュとともに表示する。ハッシュには外部メタデータを含む編集基準値を使い、取得時刻や順位には依存させない。
2. 利用者操作と、その入力を始めた時点の編集基準ハッシュを保持する。
3. 実行順が来たら、オンライン状態、認証、復旧状態、対象プロジェクトを再確認する。
4. 対象タスクの現在の編集基準ハッシュを照合する。対象が消失した場合や基準が変わった場合は送信せず、入力を残して見直しを求める。待機後の値へ基準を自動で差し替えない。
5. Asanaから対象を再取得して競合を検査し、変更対象フィールドだけをPATCHする。未指定フィールドを上書きしない。[R22]
6. Asanaから読み戻し、事後同期と順位再計算を完了する。

UIは楽観表示してよいが、読み戻し前の状態を確定扱いしない。

未保存の入力は同期済みデータと分け、同期による詳細更新やタスク選択の変更で消さない。同じタスクの未完了の保存は1件までとし、その間は対象タスクの追加編集を待たせる。別タスクの選択・編集は継続できる。遅れて届いた保存結果は対象タスクと要求を照合し、別タスクの入力へ反映しない。

対象タスクの別項目だけが同期によって変わった場合も、編集基準の不一致として保存を止める。他のタスクだけの更新では保存を止めない。競合や失敗時はAsanaの実状態と未保存の入力を区別し、未保存の入力を再送するには利用者による見直しを必要とする。

待機中に同期失敗やオフライン化が起きた場合は未実行の要求を送信せず、再接続後にも自動再送しない。書き込み後の同期だけが失敗した場合は、書き込み済みか未確認かを区別して復旧する。このとき古いキャッシュを保存結果として使わず、入力と編集基準を保持する。待機要求はメモリ内だけに保持し、オフライン変更キューとして永続化しない。

### 16.6 AI変更案の競合

変更案には生成時の基準ハッシュを持たせる。承認時に対象タスクを再取得し、フィールド単位で比較する。

- 現在値 = 基準値: 適用可能。
- 現在値 = 提案後値: すでに適用済みとして成功扱い。
- 関係ないフィールドだけが変化: マージして適用可能。
- 同じフィールドが別値へ変化: 競合。該当操作を止め、利用者へ選択を求める。

Asana APIには一般的なCASトランザクションがないため、完全に同時の同一フィールド書き込みを絶対に防げない。書き込み後の読み戻しで大半を検出し、最終的にはAsanaの実状態を表示する。

### 16.7 Custom external dataの競合

外部メタデータは、書き込み直前に再取得し、トップレベル項目ごとにマージする。

- `dependencies`: `task_gid` をキーにマージ。
- `obsidian_links`: `vault_id + path` をキーにマージ。
- `last_active_status`: 状態変更操作だけが更新。
- `activity_anchor_on`: 実質変更があった場合だけ新しい日付を採用。
- `rev`: 最大値+1。

同じ依存辺または同じノートリンクが両端末で異なる値へ更新された場合は、自動で片方を選ばず競合として要整理へ出す。

### 16.8 複数PCの収束

各PCは次を独立して持つ。

- ローカルキャッシュ。
- Events同期トークン。
- Codexスレッド。
- 未承認案。
- Vault絶対パス。
- 端末ID。

次はAsana経由で共有される。

- タスク。
- 状態。
- 重要度。
- 期限。
- 領域。
- 依存関係。
- 親子関係。
- Obsidian相対リンク。
- 停滞基準日。

同じAsana状態と同じJST日付に同期すれば、両PCの実行順位は一致する。

### 16.9 オフライン

オフライン時は読み取り専用とする。

可能:

- 最後の同期済みタスク一覧を見る。
- 最後に算出した順位と理由を見る。
- タスク詳細と既存Obsidianリンクを見る。

不可:

- GUI変更。
- AI変更案の適用。
- 新規タスク作成。
- 完了・取り下げ。
- オフライン変更キューの作成。
- 鮮度を保証できない状態でのAI変更案生成。

正常な同期、オンライン、Codex利用可能、編集可能は常時表示しない。同期中など進行中の状態、または同期失敗、オフライン、Asana認証必要、復旧待ち、Codex認証必要・利用不可、読み取り専用など対応が必要な状態だけをヘッダーに表示する。Codexがネットワーク上のモデルへ接続できない場合はチャットも利用不可となる。

## 17. 画面要件

実装画像・細かな余白の設計は本書の対象外とし、情報構造とレスポンシブ配置の切替条件を定義する。

本アプリは慣れた利用者を対象とする。自明な説明文は省き、表示面積は操作と判断に必要な情報を優先する。画面に表示しない場合も、アクセシビリティに必要な名前は維持する。
確認ダイアログ、選択欄、チェックボックス、ラジオボタン、トーストにはReka UIを使用する。
同期や編集、設定変更の完了など、消えても操作の継続に支障がない通知はトーストに表示し、一定時間で閉じる。利用者が手動で閉じることもできる。
処理中の表示、入力エラー、競合、復旧待ち、認証要求など、操作や判断に必要な情報は画面内に残す。

### 17.1 全体構成

起動時は、未完了ジャーナルの復旧、Codexの初期化、Asanaの同期より先に起動画面を表示する。起動完了後に通常画面のデータを取得し、起動完了前と失敗・停止後は機能の操作を受け付けない。

起動に失敗した場合は既存のエラー画面へ切り替え、診断情報を記録する。終了時は起動処理を中断し、その完了を待ってからサービスを停止する。

#### ヘッダー

- 「タスクハブ」の名称。
- 同期中など進行中の状態、または同期失敗、オフライン、Asana認証必要、復旧待ち、Codex認証必要・利用不可、読み取り専用など対応が必要な状態。
- 「最新の変更を取得」。
- 「全データを再取得」。
- 「AIアシスタント」と対応待ち・実行中の依頼件数。
- 「設定」。
- File、Edit、View等のネイティブメニューは設けない。

ウィンドウの最大化と全画面表示は、アプリにフォーカスがあるときに次のショートカットで操作する。

- WindowsとLinuxの `Ctrl+Shift+M`、macOSの `Cmd+Shift+M`: 最大化と通常表示を切り替える。全画面中は切り替えない。
- WindowsとLinuxの `F11`: 全画面表示を切り替える。
- macOSの `Ctrl+Cmd+F`: 全画面表示を切り替える。

通常表示時の位置・サイズと、最大化・全画面の状態を自動保存し、次回起動時に復元する。全画面を解除すると、全画面にする前の通常表示または最大化へ戻る。保存した位置・サイズが現在の画面に収まらない場合は、起動時に作業領域内へ補正する。最小化や非表示の状態は復元しない。

#### 画面幅と主要配置

画面幅はアプリの表示領域の幅をCSS pxで判定し、モニターの物理解像度は使わない。Tailwind CSSの標準境界に従い、次の配置を適用する。

| viewport幅 | 主要配置 |
|---:|---|
| 640未満 | ヘッダーの名称・状態・操作と、タスク一覧・詳細を縦方向に配置する。AIアシスタントの依頼一覧と詳細は切り替えて表示する。 |
| 640以上768未満 | `sm`。タスク詳細の状態・重要度・領域を3列に配置する。ヘッダーと一覧・詳細の配置は640未満と同じとする。 |
| 768以上1024未満 | `md`。AIアシスタントの依頼一覧と詳細を左右に配置する。ヘッダーとタスク一覧・詳細は縦方向に配置する。 |
| 1024以上1280未満 | `lg`。ヘッダーの名称・状態・4操作を同じ行に配置し、タスク一覧と詳細を左右に配置する。 |
| 1280以上 | `xl`以上。タスク関係の編集フォームと、既存の関係・子タスクをそれぞれ2列に配置し、アプリ全体を大画面レイアウトとして使用する。 |

1024 CSS px以上では、ヘッダーの4操作も横並びにする。1280 CSS px以上で大画面レイアウトを使用できるよう、今後も主要配置の切替境界を1280 CSS pxより大きくしない。

#### メイン一覧

既定で、順位対象タスクを実行順位順に表示する。表示順を変更した場合も、行に表示する順位は実行順位とし、表示位置に合わせて振り直さない。

一覧上部の「選択解除」で、タスクを選択していない状態に戻せる。並べ替えでは選択中のタスクと詳細表示を維持する。

列・情報:

- 順位。
- タイトル。
- 状態。
- 重要度。
- 設定済みの期限。
- ブロックがある場合のブロック状態。
- 子タスクの進捗 `完了数/総数`。
- 依存先の有無。
- 同期または整合性警告。

タスク行は順位とタイトルを1段目、状態・重要度・設定済みの期限・ブロック状態を本文列の2段目に配置する。2段目の情報はそれぞれラベルと値の組にし、ラベルを小さく控えめな色、値を通常色と中太字で表示する。組の間隔を確保し、狭い幅では組単位で折り返す。子タスク進捗、依存先の有無、同期または整合性警告などの追加情報は、必要な場合だけ本文列に揃えた追加行で表示する。期限日は年月日、期限日時は日本時間で表示する。重要度は1から3を通常色、4をインディゴ系、5をバイオレット系のバッジで表示する。重要度は一箇所だけ表示する。領域と短い順位理由はメイン一覧に表示しない。

「次にやる1件」を巨大表示するカードは設けない。

#### タスク詳細

- Asanaタイトルと説明。
- 状態、重要度、期限、領域。重要度は一覧と同じ色分けで表示する。期限の色と相対表示は現在入力欄にある有効な期限と状態から更新し、期限なし、未入力、入力途中はバッジを表示しない。
- 状態操作。完了、取り下げ、復元。
- 作業記録。状態は変えず、「今日の作業を記録」で活動基準日を今日へ更新し、停滞減点を更新する。
- 順位の短い要約とブロック理由。
- 初期状態で閉じた「関連ノート」。関連Obsidianノートの再解析、存在確認、ローカルで開く操作、リンク解除をまとめる。
- 初期状態で閉じた「タスク関係」。依存先・依存元、親・子タスク、`parent_work_mode`、関係編集をまとめる。
- 初期状態で閉じた「順位の計算根拠」。順位対象外や利用不可でも自動展開しない。
- Asana公式画面を開くリンク。
- 整合性警告。

広い画面では一覧とタスク詳細を横並びの2列にし、各列を画面内の高さを上限として独立して縦スクロールできるようにする。要整理一覧も展開時の高さを制限し、長い場合はその中を縦にスクロールする。内容が収まる場合はスクロールを発生させない。狭い画面では一覧と詳細を縦に並べ、ページ全体を縦にスクロールする。

#### AIアシスタントのダイアログ

ヘッダーの「AIアシスタント」から専用ダイアログを開く。ダイアログは初期状態で閉じ、タスク一覧とタスク詳細の表示領域を押し下げない。承認待ちなどへの状態変化では自動的に開かない。

ダイアログの左に依頼一覧と「新しい依頼」、右に選択した依頼の詳細を配置する。狭い画面では一覧と詳細を切り替えて操作できる。回答待ちと承認待ちを優先表示し、実行中、エラー、未確認の完了結果も一覧に残す。完了結果は確認後に片付けられる。

ダイアログを閉じる操作と依頼を中止する操作を分ける。閉じる操作や別の依頼への切り替えでも、未送信文、質問への入力、変更案の選択、編集途中の内容を依頼ごとに保持する。

未送信文の入力と、質問の選択肢から入力欄へ回答を入れる操作はローカルの編集として扱い、送信可否に連動して無効化しない。同期の開始・完了や同期済みデータの再読み込みでも、入力欄のフォーカス、選択範囲、未送信文を維持する。AIへの送信と変更案の適用は、それぞれの実行条件を満たす場合だけ受け付ける。

依頼の対象タスクは開始時に固定する。タスク未選択の状態で開始した依頼は対象タスクなしになる。変更案から対象タスクの詳細へ移動するときはダイアログを閉じ、次に開いたときは同じ依頼へ戻れる。関連ノート再解析も独立した依頼として開始する。

ダイアログ内でキーボード操作を完結でき、Escapeキーで閉じられる。閉じた後は開く前の要素へフォーカスを戻す。新規依頼の開始に成功して入力欄が有効になった後、その入力欄へフォーカスする。

新規セッションで認証が必要な場合は開始成功として扱わず、他の依頼と未承認案を保持する。Codexへのログインが必要なことをAIフィードバックで通知する。

同じダイアログ内に「外部からの提案」を置く。内部Codexが利用不可でも、Asanaの設定が完了していれば外部提案を確認できる。外部提案には出所と状態を示し、差分、理由、原文、確信度、検証結果、グループと操作の選択、編集、承認は内部AIと同じ表示・操作を使う。会話セッションとしては登録しない。外部の `review.open` は対象を保持してから画面を開き、画面の再作成や購読開始前の要求でも対象を失わない。

- Codexのストリーミング応答。
- 質問への入力。
- 変更案の差分。
- 推測箇所。
- 根拠。
- 承認、部分承認、編集、却下。
- 適用結果と競合。
- 依頼一覧から新しい依頼を開始する操作。
- 依頼の中止と完了結果の確認。

#### 設定ダイアログ

ヘッダーの「設定」から設定ダイアログを開く。ダイアログは初期状態で閉じ、通常画面の表示領域を押し下げない。外部連携の稼働状態、有効化、連携登録の案内を表示する。設定の開閉は外部連携の状態を変更しない。

### 17.2 フィルターと並び順

表示フィルターと「並び順」の選択欄は、操作対象であるタスク一覧と同じ領域にまとめる。640 CSS px未満では縦方向、640 CSS px以上では2列に配置する。

表示フィルター:

- 通常。
- 完全ブロックを含める。
- 完了を含める。
- 取り下げを含める。
- 未分類だけ。
- 領域別。
- 期限超過。
- 完了確認。
- 要整理。

要整理はヘッダーに常時表示せず、既存のフィルターで絞り込み、一覧とタスク詳細で確認する。

並べ替えはフィルター適用後の全表示行を対象とする。選択肢は次の7つとし、方向を文言で伝える。状態とタイトルによる並べ替えは設けない。

| 並び順 | 比較規則 |
|---|---|
| 実行順位順 | 既定値。順位対象・除外・利用不能を含め、Read Modelから受け取った順序を保持する。 |
| 期限の早い順 | 期限を早い方から並べる。期限なしは末尾に置く。 |
| 期限の遅い順 | 期限を遅い方から並べる。期限なしは末尾に置く。 |
| 重要度の高い順 | 重要度5から1の順に並べる。 |
| 重要度の低い順 | 重要度1から5の順に並べる。 |
| 所要時間の単位が小さい順、同じ単位では値が小さい順 | `minute`、`hour`、`day`、`week`、`month` の順に並べ、同じ単位では値の昇順とする。未設定は末尾に置く。 |
| 所要時間の単位が大きい順、同じ単位では値が大きい順 | `month`、`week`、`day`、`hour`、`minute` の順に並べ、同じ単位では値の降順とする。未設定は末尾に置く。 |

期限日はJSTの当日末、期限日時は絶対時刻として比較する。所要時間は単位間の換算を行わない。実行順位順以外は順位対象・除外・利用不能の区分をまたいで並べ替え、比較値が同じ行はフィルター適用後の元の順序を維持する。

### 17.3 要整理一覧

次を集約する。

- 重要度タグの競合。
- 領域タグの競合。
- 状態不明セクション。
- 必須セクション削除。
- 依存循環。
- 取り下げ・消失した依存先。
- 親子関係の循環。
- `children_only` 親の完了確認。
- Asana上で消失したタスク。
- Custom external data破損。
- OAuthアプリ同一性の疑い。
- AI変更案の適用結果を確定できず、人間の判断が必要な操作。
- Vaultリンク切れ。

AI変更案について要整理へ出すのは、外部書き込みが起きた可能性があり読み戻しても確定できない操作、書き込み開始後のUUID重複、安全に再開できない部分適用や第三状態、復旧計画の欠落などにより未解決と確定した操作に限る。承認時の競合、一括グループの実行阻止、書き込み前のAPI失敗、external IDの衝突、外部状態確定後のローカル再同期失敗は通常の適用結果と診断ログで示す。安全な復旧が成功した項目は要整理から取り除く。

### 17.4 GUI直接編集

オンライン時、次の基本情報は値を確定した時に自動保存する。

- タイトル。
- 説明。
- 状態。
- 重要度。
- 期限。
- 領域。

次の関係情報は、値を確定した時に自動保存する。関係編集フォームに保存ボタンは設けない。

- 依存関係。
- 親子関係。
- `parent_work_mode`。

次の操作は、利用者が対象を確認して実行した時に反映する。

- Obsidianリンクの手動解除・選択。

実行順位は編集できない。

### 17.5 「今どうなっているか」の表示

タスク一覧だけで状況を把握できるよう、各行に次を短く表示する。

- 現在状態。
- 期限までの日数または超過日数。
- ブロックがある場合のブロック理由の要約。
- 重要度。
- 子タスク進捗 `完了数/総数`。

順位とタイトルを1段目、現在状態・重要度・設定済みの期限・ブロック状態を2段目に置く。2段目は情報ごとにラベルと値を組にし、組単位で折り返す。ブロック理由、子タスク進捗、依存先の有無、同期または整合性警告は、必要な場合に追加行へ置く。期限日は年月日、期限日時は日本時間で表示する。重要度は一箇所にまとめる。順位の点数と全理由は詳細に集約する。詳細メモはObsidianまたはAsana説明へ委ね、一覧に長文を持ち込まない。

### 18.6 アプリ本体の自動更新

中央の署名処理で公開された通常版のmacOS x64とWindows x64だけを対象に、起動後にLatest Releaseを確認して更新版を自動取得する。同梱の`app-update.yml`がgeneric providerで現在版の版タグを指すことも確認する。開発実行、ローカル梱包版、未署名のedge、prerelease、対象外のOSとCPUでは確認しない。Windowsでは同じ設定に署名者名の`publisherName`がなければ更新を開始せず、設定不備を画面とエラーログへ出す。署名者名は実際の署名済み成果物で確定する。

更新メタデータと新版の配布ファイルは`https://github.com/Hiroshiba/hiho-task-management-ai/releases/latest/download/`から取得する。旧版のblockmapは`v<現在版>`のReleaseから取得する。Windowsは通常NSISを使い、NSIS Webを更新対象にしない。macOSはZIPを使う。更新の確認、取得、準備完了、失敗をMain processが保持し、Preload経由の検証済みIPCでRendererへ通知する。画面の再読込後はMain processの現在状態を取得する。

準備完了した更新は、既存の業務停止処理とウィンドウ状態の保存を終えた通常終了時に適用する。適用前に対象版の試行を`userData`へ保存し、観測した適用エラーはログへ記録する。次回起動時に実行版が対象版に達していれば試行を解消し、達していなければ適用失敗を画面とログに示す。失敗表示は次の更新確認と取得中も保ち、更新版の準備完了時に切り替える。更新失敗はアプリ全体の起動失敗にせず、業務画面を利用可能に保つ。`userData`の保存先、アプリID、SQLite、設定、外部Skillの参照先は変更しない。公開済みの`0.1.1`には更新機能がないため、初回対応版だけは手動で導入する。2版間の自動更新、署名者照合、全量取得、設定と利用者データの保持は両OSの実機で確認する。差分取得の成功は前回の更新ファイルがキャッシュにある端末で、次の版へ更新して確認する。

## 19. 認証情報と秘密管理

### 19.1 Asana OAuth設定

初期版は個人利用のため、利用者自身がAsana Developer Consoleで非公開OAuthアプリを作成する。

設定するもの:

- Client ID。
- Client Secret。
- Full permissions。
- Redirect URLとして`urn:ietf:wg:oauth:2.0:oob`を正確に登録する。

2台のPCへ同じClient IDとClient Secretを設定する。

TaskHubへClient IDとClient Secretを入力し、ブラウザで許可した後、表示された認可コードを有効期限内に貼り付ける。再認証も同じ方式で行う。認証待ち時間やローカルコールバックURLの入力は不要である。Client Secretは会話、Issue、ログへ貼らない。

パッケージへ共通Client Secretを埋め込まない。デスクトップアプリへ埋め込んだ共有secretは抽出可能であり、配布アプリの秘密として成立しないためである。

### 19.2 保存

ElectronメインプロセスでOS保護ストレージを使い、次を暗号化保存する。

- Asana Client Secret。
- リフレッシュトークン。
- アクセストークン。

Client ID、プロジェクトGID、セクションGID、Vaultパスは秘密ではないため通常設定へ保存できる。

### 19.3 プロセス間隔離

Asanaの秘密値を次へ渡さない。

- Renderer。
- preloadの戻り値。
- Codex環境変数。
- Codexプロンプト。
- `AGENTS.md`。
- `taskctl` 出力。
- 診断ログ。

### 19.4 警告・エラー時の開発者ログ

開発者向けログは、警告・エラー時に原因と発生時の状態を後から確認できるようにする。成功イベントは保存しない。

ターン実行、同期、構造化出力検証など、公開Promiseで上位へ返る未記録の失敗は、IPC等の上位境界で記録する。通知処理、プロセス終了、背景での中断要求など、IPCへ戻らない背景失敗はCodexセッションで記録する。

背景失敗が公開処理も終了させる場合や、再試行・後処理の失敗を合わせて返す場合は、記録済みの原因、未記録の原因、応答分類に使う原因を区別して型付きで伝播する。適用・復旧のcoordinatorで診断した失敗も、公開Promiseからこの記録状態を返す。診断コールバックが失敗しても元の応答原因を保持し、記録済みのみ、未記録のみ、両方の混在を型で表す。IPC、起動処理、背景処理などの上位境界は未記録分だけを保存し、応答は専用の原因から分類する。エラーメッセージの文字列やcauseをたどった推測で重複記録を除外しない。

coordinatorの診断済みの証明は、例外オブジェクトの共有identity mapに保持せず、実際のcatchと再throwの経路を通る型付きreceiptとして渡す。診断後に処理を続行する場合はreceiptを破棄し、別の失敗の記録を抑止しない。

警告・エラー時に保存する情報:

- アプリ版とCodex版。
- エラー発生時刻、処理段階、HTTPステータス、Events同期状態。
- Asana GID、proposal ID、operation ID。原因特定に必要な場合だけ記録する。
- 通常のエラーでは、例外の種別、エラーメッセージ、スタックトレース全文。causeでつながる元の例外とAggregateError内の各例外も保存する。循環参照は明示し、深さや件数による切り捨てはしない。
- 最終的なAsana REST APIのHTTP失敗は、中央transportが一度だけ正規化する。JSONLのErrorDetailにはHTTPステータス、request ID、公式ErrorResponseの `errors[]` 各要素にある `message`、`help`、`phrase` だけを共通の伏せ字処理後に構造化して保存する。非JSON、JSON破損、shape不正、本文取得不能、本文読み取りの期限超過、本文サイズ上限超過は本文を保存せず固定分類だけを保存する。
- Asana HTTP失敗をconflict、専用エラー、同期失敗状態、初回能力検査の失敗状態へ変換する場合も、元の原因を既存の最終ownerへ渡して一度だけ記録する。後続の `task_not_found` など状態確定のイベントは元のHTTP失敗と分けて記録する。
- HTTPエラー本文を読まない早期分類でもResponse bodyを有限時間で解放する。解放できない場合は本文を保存せず本文取得不能として扱い、callerの中断は既存の中断エラーとして伝播する。
- full syncが影響タスクのGET 404を`missing_gids`へ変換する場合は、削除済みタスクを観測する正常な同期結果として診断ログ対象外とする。この例外はfull syncの影響タスク取得だけに適用し、ほかの最終HTTP失敗は除外しない。
- Codex RPC操作名、数値コード、診断メッセージ、標準エラー出力、プロセス終了状態。
- 検証エラー種別。
- AI変更案の訂正試行では、セッションとターンのID、試行回数と上限、検証段階、型付きコード、候補ハッシュ、エラーのfingerprint、JSON Pointer、再試行判断。
- 適用・復旧では、操作種別、API操作、ジャーナル段階、外部書き込みの確実性、理由コード、復旧判断、試行回数、処理段階。

適用・復旧で発生したwarningとerrorは、既存のSQLite診断ログとJSONLの両方へ流す。Asanaのraw API response、request body、未知フィールド、成功応答、OAuth token endpointの応答は保存しない。最終HTTP失敗で許可する公式ErrorResponseの3フィールドは `errors[]` 各要素にある値だけとし、共通の伏せ字処理後にJSONLへ保存する。SQLiteにはHTTPステータスと安全なGID、proposal ID、operation IDだけを保存し、request IDと自由文は保存しない。原因の例外とcauseのつながりは保持する。

`journal_stage` は最後に永続化できた段階、`effect_certainty` は観測済みの外部状態を表し、独立に記録する。適用処理の読み戻しや復旧時の照合で、タスク属性とCustom external dataがともに変更後の状態と確認できた後は、ジャーナル保存に失敗しても `effect_certainty=confirmed` とする。その失敗には実際のproposal ID、operation ID、確認済みのタスクGIDを記録する。

未完了の適用ジャーナルを検出した場合は、前回適用の未完了状態を知らせる異常通知として `recovery_started` をwarningで記録する。復旧の最終結果が `applied` または `already_applied` なら成功として扱い、その成功イベントは永続診断ログへ保存しない。

共有する同期処理の診断責任は、§16.4のownerに従う。背景同期の失敗は同期ランタイムが一度記録し、診断通知のコールバックが成功した場合だけAsanaの型付き記録済みマーカーを上位へ返す。通知失敗を記録済みとは扱わず、元の失敗と通知失敗の記録状態を保持して伝播する。利用者要求が所有する同期の失敗はIPC境界で一度記録する。タイマーと利用者の要求が合流しても、同じ失敗を重複して記録しない。

タイマーが所有する同期の診断通知が失敗し、記録状態が未記録のみ、または記録済みと未記録の混在となった場合は、未記録分だけを既存のプロセスエラーバウンダリへ一度転送する。この場合はタイマーを再設定しない。

IPCはAsanaの型付き記録済みマーカーを再記録しない。応答コードの分類では、型付き記録状態の応答原因に含まれる場合も、このマーカーのcauseを一段だけ使う。通常のErrorが持つ任意のcauseは分類に使わず、causeがさらに記録済みマーカーでも展開を繰り返さない。

AI変更案の再試行はwarning、最終失敗はerrorとして、既存のSQLite診断ログとJSONLへ各イベントを1件ずつ記録する。再試行の詳細と原因構造はJSONLへ保存し、SQLiteにはcode、severity、検索用の安全な識別情報を記録する。検証失敗の本文や候補JSON、根拠、会話、秘密情報を含めず、原因のつながりを残す。

再試行イベント内の原因情報では、候補本文や根拠本文が例外のmessageへ混入し得るため、任意のmessageを保存せず、許可済みの安全な分類文へ置き換える。Error名は、コンストラクター名を検証した安全なコード由来の名前を使う。スタックはmessageを含む見出しを除き、すべてのスタックフレームに通常の永続ログと同じ伏せ字処理を適用して順序を保持する。causeの関係とAggregateErrorに含まれるすべての例外構造を、深さや件数で打ち切らず記録し、循環や共有する例外は参照で表す。

通常のエラーでは、原因を読むためのメッセージ本文、ファイルパス、スタックフレームを残し、RPC操作の種類によってエラーメッセージを除外しない。通常エラーと再試行イベントのいずれも、保存内容に含まれるトークンや認証ヘッダーなど、文字列置換で判別できる秘密値は伏せ字にする。

ログは `app.getPath('logs')/taskhub-error.log` へJSONL形式で保存し、1MBを目安にローテーションする。大きなエラー1件を上限超過だけで破棄しない。ログ書き込み自体に失敗した場合は、既存の標準エラー出力へ元の例外と書き込み失敗の詳細を出す。

次のデータ全体を診断目的で追加収集しない:

- Asana説明全文。
- Obsidian本文。
- 対象外の外部情報源の本文。
- プロンプトとCodex会話全文。

エラー調査のためにプロトコル追跡を有効にする場合も、秘密値、外部本文、プロンプトを既定でマスクする。

## 21. エラー処理

### 21.1 Asana認証

- 401: 要求が未適用であるため、アクセストークン更新を試す。[R35]
- 更新成功: 非冪等な作成要求を含め、元要求を1回だけ再実行。
- 更新失敗: 認証必要状態へ移行し、読み取り専用キャッシュ表示。
- Client ID不一致疑い: 外部メタデータ書き込み停止。

### 21.2 Asana機能・レート

- 402: 有料機能へ誤って依存したことを示す。該当機能を無効化し、ネイティブ依存関係や検索APIへ自動フォールバックしない。
- 429: 再送安全な要求だけを `Retry-After` 後に再開する。非冪等な作成要求は再送しない。
- 5xx: 再送安全な要求だけを上限付き指数バックオフで再試行する。
- 412 Events: 新トークンを保存し完全同期。
- 404 task: §13.7・§13.8の再観測対象は、その条件に従う。それ以外は削除・権限変更・移動の可能性として要整理。

### 21.3 Custom external data

- JSON破損: 生データを診断領域へ隔離し、上書きしない。
- 未知schema: 読み取り専用にし、対応版への更新を求める。
- 容量超過: 変更を拒否し、既存データを保持。
- 同時更新競合: 自動解決せず要整理。

### 21.4 Codex

- 実行ファイルなし: AI機能無効。
- 未ログイン: TaskHub専用ホームでChatGPTログインを行う導線。
- app-server初期化失敗: AI機能無効、診断情報表示。
- プロセスクラッシュ: 1回だけ再起動し、新しいスレッドを作る。
- 必要な能力またはプラットフォーム別のサンドボックスを確認できない: AI機能だけを停止する。
- Apps、Pluginsの無効設定を指定した接続、Web検索の無効設定を指定した `thread/start` に失敗: AI機能だけを停止する。
- 構造化応答、ワークスペースの未提出・参照不一致、根拠、基本・グラフ検証、適用可否の検証失敗: §13.5に従い初回を含む最大3回まで訂正する。3回目も失敗した場合はエラーを表示し、不正な案を承認UIへ出さない。
- 要求、同期、中断、外部情報の収集、外部書き込み、ターン資源の解放、診断ログ保存の失敗: AIによる訂正再試行を行わない。
- TaskHub専用ワークスペースの `AGENTS.md` またはスキル未読込: AI機能を開始しない。

Codexクラッシュ時も、既にRendererに存在する未承認案は残してよい。アプリ終了時には破棄する。

### 21.5 部分適用

AI変更案の途中で失敗した場合:

- 適用済み操作を取り消すためにタスク削除しない。
- 適用済み・未適用・不明を区別する。
- Asanaから再同期して確定する。
- 保存した承認範囲内で安全に再開できる操作は、§13.8の復旧計画に従って不足分だけを再開する。
- 外部状態が確定済みでローカル同期だけが失敗した場合は、`local_resync_required` とし、次回も§13.8の段階に従ってローカル処理だけを再開する。
- 確定できない操作だけを§17.3の要整理へ出す。承認時の競合や書き込み前の失敗は未適用として表示する。
- 必要なら修復用の新しい変更案を作る。
- 承認済みの復旧計画を超える追加修復は、利用者が承認してから書き込む。

- タグ付与・解除ができる。

## 24. 受入条件

以下は手動確認する。自動テストの実装要求ではない。

### 24.1 Asana正本

- アプリで作ったタスクが必ず専用プロジェクトに存在する。
- ローカルDBを削除してもAsanaから再構築できる。
- サブタスクも専用プロジェクトへ直接所属する。
- アプリに完全削除操作がない。
- 取り下げが専用セクションと完了フラグで表現される。

### 24.2 状態・重要度・領域

- 4状態がAsanaセクションで確認できる。
- 保留状態がない。
- 重要度1〜5がAsanaタグで確認できる。
- 領域が既存タグまたは未分類である。
- AIが新領域を提案しない。
- Asanaから直接変更した内容が同期される。
- 完了状態にしたタスクは、読み戻し後に通常一覧から除外され、完了を含めるフィルターでは同じ完了状態で表示される。
- 所要時間が一覧と詳細で同じ値として表示される。
- アプリによる書き込み後は、差分通知がなくても書き込み対象を含む同期済みスナップショットを確認し、一覧、詳細、フィルター、表示件数、順位などの派生状態が同じ事実に追従する。未確認の結果を同期成功として扱わない。

### 24.3 順位

- 同じ入力で常に同じ順位になる。
- 全順位が一意である。
- 期限なしタスクも順位対象になる。
- 期限が近いことは反映されるが、常に最上位にはならない。
- 所要時間が順位計算と活動基準日に影響しない。
- 進行中だけを理由に加点しない。
- 長期停滞タスクが規則どおり少し下がる。
- 詳細で順位理由を確認できる。
- 順位を手動変更できない。
- タスク一覧の並び順を§17.2の7つから選択でき、期限・重要度・所要時間がそれぞれの規則に従って並ぶ。
- 期限日と期限日時を混在させても時刻で比較し、期限なしと所要時間未設定はどちらの方向でも末尾になる。
- 所要時間は単位間換算をせず、同じ単位では値順になる。
- 実行順位順以外では、フィルター適用後の全表示行が順位対象・除外・利用不能の区分をまたいで並び、同値の行は元の順序を保つ。実行順位順へ戻すとRead Modelから受け取った順序になる。
- 並べ替えても行の実行順位、選択中のタスク、詳細表示、Asana上の表示順は変わらず、保存処理が発生しない。
- 選択した並び順は同期や再描画後も維持され、画面の再読み込みやアプリの再起動で実行順位順に戻る。

### 24.4 ブロック

- 各タスクがなし・一部・完全のいずれかを持つ。
- 完全ブロックは既定で隠れる。
- 一部ブロックは表示される。
- 循環依存が通常一覧から除外される。
- 子だけの親と、親自身に作業がある場合を区別できる。
- 子以外の作業がある親には順位が付く。

### 24.5 AI承認

- CodexがAsanaトークンを取得できない。
- AI変更案を承認する前にAsanaが変化しない。
- GUIの基本情報と関係情報の変更はオンライン時に自動保存する。
- タスク詳細の「順位の計算根拠」「タスク関係」「関連ノート」は初期状態で折りたたみ、順位対象外や利用不可でも自動展開しない。
- 完了・取り下げ案に根拠が必須である。
- 分割依頼なしに子タスクを増やさない。
- 未承認案はアプリ終了後に残らない。
- 部分承認・編集・却下ができる。
- 固定したAI出力で、根拠locatorとexcerptの実在、対象GIDと操作の対応、分割時の親タスク参照、基準値と競合、承認条件を検証できる。構造検証に成功しても、自然言語の意味が正しいことの証明とは扱わない。
- `base_proposal_id` を指定した追加依頼では、適用可能な前案の操作と元source、excerpt、対象、操作、分割の親を照合した対応だけを当該ターンへ結び直せる。承認UIで未選択の操作も、それだけで撤回と扱わない。対応の変更には利用可能な原文のsourceとAIの新たな意味判断が必要になる。
- 前案の状態根拠は当該ターンの基準で再確認し、利用者が変更・撤回していない操作を確認できない場合は、黙って除外せず質問する。`pending_proposal_action=keep`、生成失敗、新案の基準外部データの登録失敗では前案を保持し、新案と基準外部データの登録成功、明示的な全操作の撤回、却下、承認結果の確定に応じて前案を解放する。
- 承認画面で、アプリがsource mapまたは基準スナップショットから解決した根拠の原文と、AIの既存の理由を確認できる。AIの発言だけを根拠として表示しない。
- 対象タスク自身の `notes` を完了・取り下げの根拠にした案は、承認直前にその `notes` が変わると適用されない。
- AI生成案は全操作と全グループが適用可能な場合だけ承認UIへ出す。GUI編集によって適用不可になった操作は選択できず、案全体の承認もできない。
- 外部API前に操作全体の復旧計画を保存し、メモリ上の変更案なしでも操作順、グループ順、一括指定、一時参照、承認時の基準値を復元できる。新規作成の応答直後にGIDを保存する。
- 新規作成は `data.projects` へ対象プロジェクトGIDを1件、`data.memberships` へ同じプロジェクトGIDと目的セクションGIDの組を1件指定し、`workspace` は送信しない。作成送信と401後の再送は§13.7に従う。GIDの保存と安全な初期状態の確認を終えてから、未適用のタグと親タスクを設定する。
- 作成直後と保存済みGIDからの復旧では、§13.7・§13.8の条件に限ってGETで有限回再観測する。目的外のセクションや値の不一致は直ちに競合とし、再観測のために作成要求や追加書き込みを再実行しない。
- `prepared` の新規作成は同UUIDが0件の場合だけ開始でき、1件以上は未適用の衝突として扱う。`write_started` でGIDが不明な場合は1件だけなら照合して再開し、0件や複数件では再作成しない。
- 通常適用と復旧のいずれも、§13.7・§13.8に従って利用不能な一時参照を後続の対象・親・依存先へ使わず、連鎖する作成・書き込みを開始しない。GIDが保存済みでも、復旧開始前・復旧中のどちらで結果が確定しても、この制限を守る。参照に依存する一括グループを阻止し、独立操作を継続できる。
- タスク属性とCustom external dataの適用状況を独立に確認し、変更後に一致する側へ再書き込みしない。許可した状態・タグの部分適用だけを再開し、第三状態やマージ競合では書き込まない。
- `read_back`・`metadata_verified` の再適用・復旧は操作の外部書き込みや読み戻しを再実行せず、ローカル同期と順位再計算だけを行う。`ranking_recalculated` は最終結果の保存だけを行う。ローカル同期失敗後も、この再開範囲を維持する。
- 承認競合、一括グループの実行阻止、書き込み前のAPI失敗、external IDの衝突、外部状態確定後の同期失敗は要整理に増えず、安全な復旧が成功した項目は消える。
- 作成POSTの確定拒否は、元HTTP診断が失敗しても `journal.complete(not_applied)` が成功すればジャーナルを `not_applied` で原子的に確定し、未記録分を上位へ伝播する。completionに失敗した場合だけ復旧待ちの状態を保ったまま上位へ伝播し、次回は永続化済みの `write_started` に従って保守的に復旧する。作成POSTを再送しない。
- 正常な保存済みの計画では、永続化済みの段階と観測済みの外部状態から未適用と確定できる処理だけを再開する。`final_result=unknown` を外部状態の再取得や書き込みの対象にせず、復旧計画の破損・欠落や不整合データとともに個別の手動解消へ委ねる。

### 24.6 Codex

- 実際のCodexプロセスを起動している。
- ChatGPTサブスクリプション認証を利用できる。
- TaskHub専用 `CODEX_HOME` を使用し、通常のCodexホームの設定やセッションを継承しない。
- アプリ起動ごとに新しいスレッドになる。
- ヘッダーから依頼一覧と詳細のダイアログを開き、新しい依頼を開始できる。
- ダイアログを閉じても依頼の実行と入力状態を保持する。
- 同期完了通知から一覧再読み込みまでの間も、AI入力欄のフォーカス、選択範囲、未送信文を保持する。送信できない間も未送信文を編集でき、質問の選択肢を入力欄へ反映できる。
- 複数の依頼を独立したスレッドで並行実行し、応答や承認対象が混ざらない。
- 各依頼と応答が古い順に表示され、質問の本文を履歴から確認できる。
- 応答中の表示と最終応答が重複せず、入力欄が会話の末尾にある。
- 送信失敗が会話履歴で失敗として表示される。
- 別の依頼が回答待ち・承認待ちでも新しい依頼を開始できる。
- 変更案から対象タスクへ移動し、同じ依頼へ戻って承認できる。
- 完了結果は確認後に片付けられ、明示的な中止は対象の依頼だけを停止する。
- 新規セッションで認証が必要な場合は開始成功や入力欄へのフォーカスを行わず、Codexへのログイン要求をAIフィードバックで通知する。
- アプリ終了前のスレッドを復元するUIがない。
- TaskHub専用ワークスペースの `AGENTS.md` とスキルが読み込まれる。
- モデル取得とプラットフォーム別の制限付き `thread/start` を確認できる。Windows以外ではTaskHub専用権限プロファイルも確認できる。
- AppsとPluginsの無効設定を指定した接続、Web検索の無効設定を指定した `thread/start` が成功する。
- 全OSで、内部AIが `proposal_workspace` の `read`、`edit`、`diff`、`validate`、`submit` を使って変更案を構築できる。別スレッド・別ターン・別ワークスペースからの操作と、終了したターンへの遅延要求を拒否する。
- 編集バッチは全操作を原子的に反映し、失敗時に改訂番号や候補を変更しない。同じバッチIDと内容の再送は再適用せず、内容の不一致や古い改訂番号を拒否する。移動と操作の置換でIDを保持し、編集中の不備は提出までに修正できる。
- 引数は128 KiB、応答は64 KiBの上限を守る。大きな案を複数バッチで編集し、概要・グループ・操作の部分読み取り、改訂番号間の差分、検証エラーの続き取得ができる。
- `validate` は案を変更せず、`submit` は完成案の検証が成功した場合だけ封印する。封印後の新たな編集を拒否し、提出だけでは承認UIへ公開しない。
- Structured Outputs互換の外側スキーマによりCodexターンが完了し、復号後の `response_json` を厳格に検証できる。変更案では提出済みの `workspace_id` と `revision`、説明、質問を受け取る。復号後のUTF-8で96 KiB、外側の200,000文字と256 KiBの上限を守る。
- ターン成功後、提出済みワークスペースと最終応答のID・改訂番号の一致、根拠、基本・グラフ検証、全操作と全グループの適用可能性を確認した案だけを保持して公開する。提出後の失敗や中断でも新案を公開せず、前案を保持する。
- 初回を含む最大3回まで訂正でき、同じ候補内容も試行回数を消費する。再試行ごとに新しい基準とワークスペースを発行し、引き継ぐ候補の変更前値と根拠を結び直す。次のプロンプトとツール応答から検証エラーを確認できる。
- 変更案と検証エラーはメモリに保持し、Codex作業ディレクトリにファイルを作成しない。ターン終了時にツール操作を無効化し、ターン資源を解放してから結果を確定する。要求、同期、中断、外部情報の収集、外部書き込み、ターン資源の解放、診断ログ保存の失敗ではAIによる訂正を繰り返さない。
- 実AI生成で、対象を一意に特定した利用者の完了報告からは余計な確認なしに完了案を提示できる。引用、否定、伝聞、仮定、条件付きの記述を完了報告と誤認せず、対象の取り違えや未完了部分の完了扱いをしない。
- 実AI生成で、完了の事実報告、取り下げの意思、分割の明示依頼、取り下げ確認への肯定を区別できる。独立タスクの列挙は分割にならず、取り下げ対象が曖昧な場合は同じ依頼内で候補1件を確認できる。
- 同じAIワークフローサービスのインスタンスでは、質問後の短い回答や `base_proposal_id` のない要求でもsource mapの過去原文を参照してAIが意味を判断できる。失敗・中断した現ターンの未確定原文は後続の根拠にならない。設定変更や確認リセットだけでは成功した原文を失わず、別のサービスのインスタンスやアプリ再起動後に過去の原文を根拠として再利用しない。
- 必要な能力やプラットフォーム別のサンドボックスを確認できない場合は、AIだけが安全に停止する。

### 24.7 Obsidian

- Obsidianを変更しない。
- 関連情報は相対パスとタイトル中心で、Asana説明を汚さない。
- 関連ノートが0件のタスクを対象にしたAIセッションでも、登録済みVaultの検索と本文取得ができる。
- AIからの確認に検索語を追加回答したあとも、同じ依頼でノートを検索できる。
- 最新メモは更新日時の降順で取得され、日時が同じ場合の順序も一定になる。
- AIの読み取り要求で未登録Vault、Vault外のパス、取得上限違反を拒否し、Windowsのサンドボックス権限を緩めない。

### 24.8 複数PC・オフライン

- 同じOAuth Client IDを使った2台で外部メタデータが見える。
- 同期後、同じJST日付なら順位が一致する。
- Vaultの絶対パスを端末ごとに設定できる。
- オフライン時は読み取り専用になる。
- オフライン変更キューを作らない。
- 同一フィールド競合を検出し、黙って上書きしない。

### 24.9 セキュリティ

- RendererにNode.js権限がない。
- RendererからAsanaトークンが見えない。
- IPCが操作単位で狭く定義される。
- Codexのシェルに任意ネットワーク権限がない。
- アプリからAsana削除APIを呼ぶ経路がない。
- 警告・エラー時の開発者ログは§19.4の役割に従ってSQLiteとJSONLへ記録する。内部AIへの訂正用情報はメモリに保持し、プロンプトとツール応答で渡す。再試行はwarning、最終失敗はerrorとし、各イベントが両ログに1件ずつ記録される。成功イベント、秘密情報、提案本文、根拠本文、Asanaのraw API response、外部本文、プロンプトを診断情報に保存しない。最終Asana HTTP失敗で許可する公式ErrorResponseの `errors[]` 各要素の3フィールドは、JSONLに限り伏せ字後に保存する。

### 24.10 レスポンシブ配置

- 640、768、1024 CSS pxの前後で、画面幅と主要配置の表どおりに切り替わる。
- タスク一覧の表示フィルターと並び順の選択欄が639 CSS pxでは縦方向、640 CSS pxでは2列に配置され、長い選択肢も操作できる。
- 1024、1279、1280 CSS pxと、それより広い画面で、ヘッダーの名称と4操作が同じ行に収まり、タスク一覧と詳細が左右に配置される。
- タスク関係を展開し、編集フォームと既存の関係・子タスクが1279 CSS pxでは1列、1280 CSS pxでは2列になる。
- 1280 CSS px以上では、AIアシスタントも含めて大画面レイアウトを使用できる。
- 狭い画面で内容が横にはみ出さず、一覧と詳細の情報を操作できる。

### 24.11 外部Codex連携

- WindowsとWSL、macOSのターミナルから同じPCの配布版へ接続でき、日本語、空白、引用符を含むパスとJSONの標準入出力、終了コードを扱える。
- 実際のCodexの権限設定で専用ランチャーを実行でき、明示Skillは使える一方、通常の会話で暗黙に選択されない。
- 初回登録、同じ登録の再実行、同名Skillやルールとの競合、連携の無効化、アプリ停止、更新後の起動を確認する。
- 本体更新後にSkillを再インストールせず、プロトコル3の `agent-info` から操作仕様を取得できる。プロトコル、起動インスタンス、接続先の文脈が一致しない要求を拒否する。
- 6種類の読み取りが内部の `taskctl` と同じ条件と応答を使い、オフラインのキャッシュと同期時刻を示す。読み取りから同期やAsanaへの書き込みを開始しない。
- 準備で発行した `proposal_context_id` により固定スナップショットを読み、`workspace_id` を指定して案を構築できる。初回の `replace_all`、分割構築、IDを保った追加編集、差分取得を通じて、同じ基準で全17操作と複数グループを扱える。提出時に基準を取り直さず、準備後にAsanaで変更された値は承認時に競合として検出する。
- 編集バッチは原子的に適用し、失敗したバッチでは案と改訂番号を変更しない。同じ `edit_batch_id` と内容の再送では初回の結果を返し、異なる内容や古い改訂番号を拒否する。`stale_revision` の `current_revision` で現在の案を読み直せる。
- 読み取り、差分、検証結果は応答上限63 KiBを守って続きを取得でき、分割したJSONから元の案や差分を復元できる。検証結果の操作判定と基本・グラフ診断は `entries` と `entry_count` で、不備は `issues` と `issue_count` で扱い、最大50項目ずつ読める。長文メッセージの省略は `message_truncated` で示す。
- 完成形のスキーマ、基準ハッシュ、全操作の原文根拠を満たす案だけを提出できる。`can_submit=true` でも基本・グラフ検証が不適合の操作はレビューへ残り、適用可能な範囲をGUIで選択できる。
- 提出は準備と別の `request_id` と現在の `expected_revision` を使い、成功すると案を封印して承認待ちにする。不備のある提出は編集可能なままとし、修正した改訂番号を新しい要求IDで提出できる。提出成功時の再送は同じ提案IDと現在状態を返す。
- 内部Codexが利用不可でも、共通の差分・根拠・検証表示で外部提案を編集、却下、承認でき、適用するグループや非一括の操作を選択できる。外部CLIからは承認できない。
- 全操作に保存した原文と操作ごとのlocator、空でない正確なexcerptが必要になる。完了、取り下げ、分割は対応する明示根拠も一致させ、別操作のlocatorや原文にないexcerptを根拠にできない。GUI承認時には選択した操作の根拠を再検証する。
- 準備と提出の同時再送、GUI編集後の再送、古い版からの操作、二重承認、内部AI案との同時承認、接続先変更、応答喪失を通じて基準や提案を二重に作らず、変更を二重適用しない。
- 基準値取得中の再認証、無効化と再有効化、アプリ終了で固定した基準と未承認案が復活しない。受付後に基準値取得が失敗しても、同じ要求IDの再送で準備をやり直さない。
- アプリ終了で固定したスナップショット、利用者原文、ワークスペース、未承認案を破棄する。状態照会は提出前の概要から保持した全操作IDを同じ順序で受け取り、メモリにある提案のメタデータ・状態・適用結果と再起動後のジャーナル照会を区別し、部分承認と結果不明を操作ごとに示す。
- 不正なcapability、過大な要求、同一IDの異なる内容を拒否し、接続情報と診断から秘密値が漏れない。

### 24.12 アプリ本体の自動更新

- 署名済み通常版のmacOS x64とWindows x64で起動後に最新版を確認し、新版を取得して通常終了時に適用する。更新の確認、取得、準備完了、失敗が画面に届き、画面の再読込後も現在状態を表示できる。適用後に同じ版で起動した場合は失敗を画面とログで確認でき、更新確認中も失敗表示が消えない。対象版以降で起動した場合は適用試行を解消する。
- 同時に更新確認を重ねず、開発実行、ローカル梱包版、edge、prerelease、対象外のOSとCPUでは更新しない。Windowsで署名者名が配布設定にない場合は取得せず、画面とログに失敗を記録する。
- 更新に失敗しても業務画面を利用でき、通常終了時の既存の停止処理、ウィンドウ状態、設定、SQLite、外部Skillの参照先を保持する。
- 2版の署名済み通常版で、署名者照合、全量取得、両OSでの適用、設定と利用者データの保持を実機で確認する。前回の更新ファイルをキャッシュした状態で次の版への差分取得と失敗時の全量取得を確認する。初回対応版は`0.1.1`から手動で導入し、自動更新未確認と記録する。

## 25. 既知の制約とリスク

### 25.1 Asana OAuthのClient Secret

Asana OAuthはトークン交換でClient Secretを要求する一方、一般的なデスクトップアプリは秘密を完全には隠せない。初期版は一人利用なので、利用者自身の非公開OAuthアプリのSecretをOS保護ストレージへ保存する方式を採用する。

第三者配布する製品へ発展させる場合は、共有Secretをバイナリへ埋め込まず、認証バックエンドを持つ構成へ再設計する必要がある。

### 25.2 Full permissions

OAuthトークンは広い権限を持つ。アプリ内許可リストは誤操作防止には有効だが、漏えいしたトークン自体の権限を狭くするものではない。OS保護、Renderer隔離、Codex隔離が必須である。

### 25.3 Custom external dataのアプリ分離

別Client IDではデータが見えない。2台で同じOAuthアプリを使う運用が必須である。

### 25.4 Asanaの同時更新

Asana APIに一般的な原子的CASがないため、完全に同時の同一フィールド更新を数学的に排除できない。再取得、フィールド単位比較、読み戻しで検出範囲を最大化する。

### 25.5 Asana公式UIで見えない情報

依存関係、Obsidianリンク、停滞基準日はAsana公式UIに表示されない。これは無料範囲と説明欄非汚染を両立するための意図的な制約である。

### 25.6 Asanaからの完全削除

アプリは完全削除しないが、Asana公式UIで利用者が削除することは防げない。検出と警告はできるが、自動復元はしない。

### 25.7 app-serverの版差異と残余リスク

Codex app-serverはリッチクライアント向け公式インターフェースである一方、Codex版ごとの未公開機能を完全には監査しない。版文字列で事前拒否せず、検出したCodexを起動して必要な能力とプラットフォーム別のサンドボックスを確認する。必要な能力またはサンドボックスを確認できない場合はAI機能だけを停止する。

Windowsの非昇格サンドボックスでは、実効ポリシーが `workspaceWrite` の場合に専用作業ディレクトリ全体が書き込み可能になり、`readOnly` の場合もモデル側コマンドの読取範囲から専用 `CODEX_HOME` とVaultを除外できない。これはWindows版をまず動作させるために受け入れる制約である。Asana資格情報と書き込み手段はCodexへ渡さず、Codexシェルのネットワークも無効にする。`dangerFullAccess` と `externalSandbox` が返された場合はAI機能を停止する。[R23]

### 25.8 サブスクリプション利用上限

OpenAI API課金は使わないが、CodexのChatGPTサブスクリプション側の利用上限・接続要件は残る。上限到達時も、Asanaの通常閲覧・GUI編集は利用可能にする。

### 25.9 自動テストなし

自動テストを実装しないため、順位式、同期競合、認証、サンドボックス変更時の回帰リスクは高くなる。要件上はそのままとし、起動時能力検査、入力検証、診断ログ、手動受入確認で補う。

## 28. 最終仕様要約

- Asana Personalの1専用プロジェクトが唯一のタスク正本。
- 状態は未着手・進行中・完了・取り下げの4セクション。
- 重要度1〜5、領域、ブロック状態はAsanaタグで可視化。
- 期限は任意。所要時間は任意で、粗い単一単位の見積をCustom external dataへ保存する。
- 所要時間、依存関係、Obsidianリンク、停滞基準はOAuthアプリ固有のCustom external data。
- 完全ブロックは既定非表示、一部ブロックは減点して表示。
- 親自身に作業があり得る場合は親にも順位を付ける。
- 順位は重要度、期限、解放効果、一部ブロック、停滞から固定式で一意に算出。
- AIは実順位を決めず、入力値と変更を提案するだけ。
- Codexは実際の `codex app-server` をTaskHub専用 `CODEX_HOME` でChatGPTサブスクリプション認証により起動。初回に専用ホームで一度ログインし、通常ホームの認証ファイルをコピーしない。
- Windows以外ではPATHで検出したCodexのシンボリックリンクを実体パスへ解決し、実体ファイルだけをTaskHubの権限プロファイルで読み取り許可する。
- 通常のCodexホームの設定、MCP定義、プラグイン、ホーム側スキル、セッションを継承しない。
- 検出したCodex版を実際に起動し、モデル取得、TaskHub専用ワークスペースの `AGENTS.md` とスキル、プラットフォーム別の制限付き `thread/start` を確認する。Windows以外ではTaskHub専用権限プロファイルも確認する。版文字列で事前拒否しない。
- 起動ごとに新規スレッド。過去復帰、会話同期、Git保存なし。
- 接続時にAppsとPluginsを無効化し、スレッドのWeb検索を無効化する。通常設定のMCP二段階探索、実行時のMCP名変換、未知機能の許可リストは行わない。
- CodexにAsana認証・書き込み手段を渡さない。
- AI変更はすべて構造化案、検証、利用者承認を経て反映。
- 全OSで、内部Codexは当該ターンのメモリ上のワークスペースをdynamic toolで読み取り・編集・検証・提出し、最終応答で提出済みのIDと改訂番号を返す。ターン成功後に参照を照合し、根拠と全操作の検証を通った案だけを承認UIへ公開する。訂正可能な失敗は初回を含む最大3回まで、新しい基準とワークスペースで訂正する。
- Codex出力はStructured Outputs互換の外側オブジェクトで受け取り、内側の `response_json` を既存のTaskHub応答スキーマで厳格に検証する。復号後はUTF-8で96 KiB以下とし、外側の200,000文字と256 KiBの上限も守る。
- 外部Codexはプロトコル3のCLIで基準と原文を固定し、ワークスペースを部分編集して提出する。完成形と全操作の原文根拠を受付条件とし、基本・グラフ検証の不適合はGUIの部分採用レビューへ残す。選択した操作だけをGUI承認後に適用する。
- 承認済み操作は外部API前に復旧計画を永続化し、起動時に正常な保存計画と永続化済みの段階、Asana実状態から不足分だけを再開する。作成結果不明の再作成や、適用済みの側への再書き込みはしない。`unknown`、復旧計画の破損・欠落、不整合データは個別に手動で解消する。
- GUIの基本情報と関係情報の変更はオンライン時に自動保存。
- AIによる完了・取り下げは明示的根拠がある場合だけ。
- タスク分割は明示依頼時だけ。
- Obsidianは読み取り専用。Discord等の外部情報源連携は初期版の対象外。
- 未承認案はアプリ終了時に破棄。
- ローカルSQLiteには再構築可能なキャッシュ、承認済み操作の復旧ジャーナル、診断ログを保存する。
- 複数PCは同じAsana OAuthアプリを使用し、Asana同期後に同じ順位へ収束。
- オフラインは読み取り専用で、変更キューなし。
- 完全削除なし。すべて取り下げ。
- AI変更案の要整理は人間の判断が必要な未確定操作に限り、安全な復旧後に解消する。承認競合や外部状態確定後のローカル同期失敗は通常結果とログで示す。
- 開発者ログは警告・エラー時に原因と状態を追える安全化情報だけをSQLiteとJSONLへ保存し、成功イベント、秘密値、提案本文、Asanaのraw API response、外部本文、プロンプトを保存しない。最終Asana HTTP失敗の公式ErrorResponseの `errors[]` 各要素にある `message`、`help`、`phrase` は伏せ字後にJSONLへ保存し、SQLiteにはHTTPステータスと安全な識別子だけを保存する。
- 必要な能力またはプラットフォーム別のサンドボックスを確認できない場合はAIだけを停止し、Asana機能を継続する。Codex版ごとの未公開機能を完全に監査しないことは残余リスクとする。
- Electron / Vite / TypeScript / Vue / Reka UI / Tailwind CSS / pnpm、Windows / macOS。
- 自動テストは実装しない。
